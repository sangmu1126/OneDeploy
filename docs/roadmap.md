# 남은 작업 로드맵

기준: 2026-10-06. 이 문서는 **아직 하지 않은 작업**을 한곳에 모은다. 구현·검증된 범위는
[현재 상태](status.md), 실환경 실행 조건과 합격 기준은
[후속 실환경 검증 계획](deferred-verification.md), 독창성 설계는
[독창성 설계](originality-design.md), 요구사항(R-xx)은 [요구사항 명세](requirements.md), 목표 구조는
[목표 설계](target-design.md)를 따른다.

## 작업 원칙 (2026-10-06 개인 계획)

OneDeploy 개인 프로젝트의 계획이다. Sky 팀의 합의나 팀 저장소 작업 목록은 아니다.

- **보완하고, 삭제·축소하지 않는다.** 불필요해 보이는 부분은 근거와 함께 정리 후보로
  올리고, 결정은 프로젝트 소유자가 한다(아래 "정리 후보").
- **해커톤용으로 축소하지 않는다.** 실무에 적용할 수 있는 수준을 목표로 한다.
- **OpenAI API 키는 최대한 늦게 쓴다.** 기능 개발과 테스트는 고정 응답(`--wire-fixture`
  등)으로 진행한다. 실제 모델 검증은 마지막에 한 번에 묶어 실행한다. 문제를 고칠 시간을
  남기기 위해 실행 마감을 10/8로 제안했다(미확정). OpenAI 프로젝트에 예산 한도를 걸고,
  첫 실행에서 배포 1회 비용을 측정해 기록한다.
- **검증하지 않은 것은 완료로 표시하지 않는다.** 고정 응답, 모의 AWS, 로컬 검증을 실제
  모델·실계정 검증과 구분한다.

## 축 1 — 이식성 실증

환경이 달라도 같은 앱을 안전하게 배포할 수 있는지 증명한다.
[이식성 청사진](portability-blueprint.md)의 순서를 따른다.

순서 원칙(2026-10-06 개인 계획): **공통 어댑터 계약 고정 → 같은 앱의 Local·AWS 교차 검증
(같은 이미지 승격으로 구현) → 가능하면 Cloud Run 실배포 → 대상별 결과를 갖춘 다중 대상
배포.** 단일 대상 이식성을 실증하기 전에 다중 대상 버튼부터 만들지 않는다.

| 순서 | 작업 | 현재 | 비고 |
| --- | --- | --- | --- |
| 0.5 | **실행 방식 선택** (R-11) | 없음. 모든 앱을 컨테이너로 배포 | 출제자의 첫 질문 "어디에, 어떤 방식으로"에 대응. 먼저 정적 사이트와 HTTP 서버를 구분하고, 정적 사이트는 컨테이너로 감싸는 이식성 기본 경로부터 구현. S3+CloudFront 같은 고유 기능 경로는 그 뒤. [목표 설계](target-design.md) 4.2절 |
| 0 | 공통 어댑터 계약 고정 | `TARGET_CAPABILITIES` 등 일부 | 기능 선언, 사전 검사·비용, 산출물 수신, 배포·검증, 드릴 수단, 소유권·정리, 결과 보고. [독창성 설계](originality-design.md) 7.1절 |
| 1 | 대상별 요구사항 검사 완성 | 저장소·DB·CPU 아키텍처 검사 일부 구현 | 네트워크, 비밀값, 필수 환경변수까지 배포 전에 판정. 결과는 독창성 설계의 **환경 차이 지도**로 보여준다 |

| 3 | DB의 AWS 종속성 분리 | RDS 생성·연결·백업이 AWS 구현에 결합 | 앱의 논리적 데이터 요구와 RDS 절차를 분리 |
| 4 | 실제 데이터 이전 검증 | 범용 데이터 이전 기능 없음 | 스키마·데이터 보존, 전환 실패 시 복구까지 시험 |
| 4.5 | **SQLite → PostgreSQL 전환** (R-31) | 차단 중 | 출제자의 첫 번째 예시. 차단 결정을 뒤집고 좁은 지원 범위로 설계: 원본 보존, AI 코드·스키마 변환, 로컬 리허설 이전, 새 빈 DB로만 이전, 행 수·표본 해시·앱 읽기/쓰기 검증, 실패 시 전환하지 않음. [목표 설계](target-design.md) 4.5절 |
| 5 | Cloud Run 실계정 배포·승격 | 어댑터 테스트만 통과 | **행사 요구사항의 필수 조건은 아니다.** 브리프는 클라우드 선택이 자유이고 Local·AWS로 충족된다. "여러 클라우드에서 증명했다"고 말하기 위한 선택적 목표. GCP 프로젝트·과금 준비 필요 |
| 6 | 다중 대상 배포 그룹 | 없음. 작업 하나가 대상 하나 | 같은 다이제스트를 공유하는 대상별 작업 N개. 대상별 상태·비용·정리·재시도·증명서를 독립 관리하고 전체 결과는 `부분 성공`까지 표현. 5번 이후 구현. 독창성 설계 7.2절 |
| 7 | 온프레미스 원격 서버 어댑터 | 같은 PC의 Docker만, `127.0.0.1` 전용 | `DOCKER_HOST` 변경으로 끝나지 않는다. 이미지 전달, 외부 URL, SSH 권한, 데이터 위치, 소유권·정리를 별도 어댑터로 구현·검증. 독창성 설계 7.3절 |

## 축 2 — 운영 수준

실무에서 쓸 수 있는 배포 시스템으로 만든다.

| 작업 | 근거 | 우선순위 |
| --- | --- | --- |
| **배포 후 자동 드릴** (재시작 내성, 롤백 리허설, AI 예측 채점, 백업 복원 드릴) | 독창성의 핵심. 배포 성공 뒤 비동기로 실행해 배포 시간을 늘리지 않는다 | 높음 |
| **앱 비밀값을 비밀 저장소로 이동** | 사용자가 입력한 환경변수가 ECS 태스크 정의에 평문 `environment`로 들어간다([aws.py](../onedeploy/aws.py)의 컨테이너 정의). DB 비밀번호처럼 Secrets Manager를 쓰도록 맞춘다 | 높음 (보안, 범위 작음) |
| **실행 자격 증명 분리** | 지금은 개발자 개인의 AWS·gcloud 로그인을 그대로 쓴다. 최소 권한 역할(AssumeRole, 서비스 계정 가장)로 바꾼다 | 높음 |
| **다중 사용자와 동시 배포** | 단일 랜덤 토큰, 127.0.0.1 전용, JSON 파일 상태. 인증·권한, 행위자 기록 감사 로그, 교체 가능한 상태 저장소가 필요하다 | 중간~높음 |
| **카나리·블루그린 배포** | 지금은 AWS 롤백만 있다. 운영 서비스에서 롤백 리허설을 하려면 전제 조건이다 | 중간 |
| **CI/CD 연동** | Git push 트리거, GitHub Actions OIDC. 사람과 CI가 같은 배포 API를 쓴다 | 중간 |
| **관측성** | HTTP 상태 확인뿐이다. 로그 수집(CloudWatch, Cloud Logging), 지표, 경보, 시각화 | 중간 |
| **AI 비용 측정** | 배포 1회당 토큰·비용과 AI가 줄인 작업을 기록 | 중간 |
| **업로드 코드 빌드 격리** | 신뢰할 수 없는 Dockerfile을 개발 PC의 Docker에서 직접 빌드한다. 격리된 빌드 실행기 필요 | 중간 |
| **지원 앱 범위 확인** | Next.js, 정적 SPA, Rails, Hono를 시험한 기록이 없다. 확인된 것은 Node, Python, 기존 Dockerfile 앱 | 중간 |
| **AI 제공자 분리** | OpenAI 엔드포인트와 OpenAI 전용 기능(`responses/compact`, 암호화된 추론 내용 재전달)이 코드에 고정돼 있다. Infinite Clouds 원칙을 AI 계층까지 적용하려면 AI 제공자도 배포 대상처럼 환경에 맞춰 교체할 수 있어야 한다. 행사까지는 클라우드에 묶이지 않는 OpenAI를 유지하고, 이후 Amazon Bedrock 등을 선택지로 추가한다. 분리하면 로컬 모델로 키 없이 리허설할 수도 있다(최종 검증 대체는 아님). 판단 근거는 [의사결정 기록](decision-log.md) 2026-10-06 | 중간 |
| **복원 드릴을 제품에 연결** | 복원 검증 모듈 9개가 CLI 전용이다. 배포 후 드릴(백업 복원)로 통합한다 | 낮음 |

## 구조 정리

새 기능을 넣기 전에 하면 이후 작업의 위험이 줄어든다.

- [server.py](../onedeploy/server.py) 분리: 약 2,000줄, 라우팅 함수 `handler_for` 하나가 약 700줄.
- `except Exception` 61곳 점검: 실패를 넓게 삼키는 곳이 있는지 확인.
- [index.html](../onedeploy/static/index.html) 정리: 73KB가 141줄에 들어 있고 한 줄이 최대 약 7,500자.

## 결정 대기

- **전체 작업 순서:** 이식성 축의 순서는 개인 계획으로 정했다(축 1 맨 위). 남은 결정은 그 앞뒤에
  `server.py` 분리와 실행 자격 증명 분리를 어디에 둘지다. 제안은 `server.py` 분리를 가장
  먼저 하는 것이다. 독창성 설계 11절의 구현 순서와 함께 확정한다.
- **OpenAI 실검증 마감:** 10/8 제안.
- **출제 의도 해석의 확인:** 멘토 확인 질문 4개의 답에 따라 실행 방식 선택과 SQLite 전환의
  범위를 조정한다.
- **행사 AI 비용 지원의 대상 업체:** PDF에 세부 내용이 없다. AWS 크레딧으로만 지원된다면
  AI 제공자 판단(OpenAI 유지)을 다시 검토한다. 운영진에게 확인한다.
- **GCP 프로젝트·크레딧 사용 가능 여부:** Cloud Run 실계정 검증의 전제.
- **팀 프로젝트 반영 범위:** 개인 사전 작업 중 Sky 팀 저장소에 채택할 내용을 팀과 별도로 정한다.
