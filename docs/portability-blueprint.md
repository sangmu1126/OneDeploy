# 환경 차이 극복과 이식성 청사진

OneDeploy의 이식성은 **같은 앱의 요구사항을 한 번 분석하고, 지원하는 대상마다
동등한 실행 조건을 구성·검증하는 능력**이다. OCI 이미지로 포장되는 것만으로
데이터·네트워크·비밀·URL·운영 정책까지 옮겨지는 것은 아니다. 대상이 요구사항을
충족하지 못하면 조용히 다른 구성을 만들지 않고 배포 전에 이유를 알려준다.

## 공통 계약

앱 분석 결과는 클라우드 이름이 아닌 다음 요구로 기록한다.

| 영역 | 공통 계획에 남길 내용 | 대상별 검증 |
| --- | --- | --- |
| 실행 | 런타임·진입점, 빌드 대상 아키텍처, 포트·상태 경로, 필수 환경변수 | 이미지 빌드와 실제 HTTP 응답 |
| 상태 | 무상태 여부, DB·파일·세션·백그라운드 작업 요구 | 재시작·릴리스 교체 뒤 데이터 보존 |
| 네트워크 | 공개/비공개 접속, 외부 통신, DB 접속, 도메인·TLS 요구 | 실제 엔드포인트와 접근 범위 |
| 운영 | 비밀 주입, 로그, 헬스 검사, 확장·비용 한도, 종료·복구 | 소유 리소스와 실패 후 상태 |

AI는 소스 근거와 함께 이 계약에 필요한 코드 변경을 제안한다. 서버는 변경 전후의
요구사항을 다시 검사하고, 대상 어댑터의 기능과 대조한다. 원본 소스는 보존하며
대상 전용 수정은 작업용 복사본과 변경 기록에서 구분한다. 예를 들어 앱이 로컬
파일을 영구 저장해야 하는데 대상이 휘발성 파일시스템만 제공하면 무상태 웹 앱으로
성공 처리하지 않는다.

## 대상 기능과 환경 바인딩

공통 계획은 `서비스`, `영속 데이터`, `비밀`, `네트워크`, `검증`, `정리`라는
논리적 요구를 표현한다. AWS ECS/RDS, Cloud Run, Local Docker의 어댑터가 이를
각자의 자원과 설정으로 변환한다. 어댑터마다 공개 접근, 영속 저장소, 워커,
아키텍처, 비밀 관리, 롤백, 비용 상한의 지원 여부를 명시한다. 자동 대상 선택은
사용 가능한 계정·권한뿐 아니라 이 기능표를 만족하는 대상만 후보로 넣는다.
사용자가 대상을 지정해도 같은 검사를 적용한다.

현재 `linux/amd64` 이미지 빌드, 환경변수 전달, 공통 HTTP 확인, 대상별 리소스
소유권 검사에는 공통 경로가 있다. AWS PostgreSQL 구성은 RDS·ECS 비밀·VPC에
결합돼 있다. Cloud Run의 실계정 배포와 DB 경로, 온프레미스 배포, 여러 대상의
동시 배포는 검증된 기능으로 표시하지 않는다. 새로운 어댑터를 추가할 때 기존
AWS 필드나 Terraform 상태를 공통 계약에 그대로 노출하지 않는다.

## 데이터 이동은 별도 절차

앱 배포와 데이터 이전은 독립된 작업으로 다룬다. 같은 PostgreSQL 엔진이라도
백업·복원 또는 논리적 덤프, 스키마 버전, 비밀 교체, 접속 전환, 데이터 정합성,
원본 보존과 롤백 기준이 확인돼야 대상 변경을 완료한다. SQLite→PostgreSQL 같은
엔진 변경은 스키마·쿼리 변환과 데이터 검증이 따로 필요하다. 현재 구현의 SQL
마이그레이션은 **선택한 AWS RDS의 스키마 업데이트**이며, 데이터베이스를 다른
환경으로 옮기는 기능이 아니다. 이 구분을 API와 UI 결과에도 유지한다.

## 구현 순서와 완료 기준

1. **계약과 기능표 고정:** 기존 정적 탐지·AI 계획·실행 설정을 공통 요구 형태로
   묶는다. 지원하지 않는 상태 저장·네트워크·아키텍처 조건은 리소스 생성 전에
   차단하고 근거를 작업 이력에 남긴다.
2. **무상태 앱의 교차 대상 검증:** 동일한 소스와 계획으로 Local Docker와 AWS에서
   빌드·배포·HTTP·종료를 확인하고, Cloud Run은 실계정 설정이 준비되면 같은
   검사를 수행한다. 대상별 URL, 공개 범위, 로그·실패 복구 차이를 기록한다.
3. **영속 데이터 경계 분리:** AWS RDS 경로의 생성·접속·SQL 실행·백업·폐기를
   공통 요구와 AWS 구현으로 분리한다. 다른 대상의 DB 어댑터가 준비되기 전에는
   DB 앱의 대상 변경을 지원한다고 표시하지 않는다.
4. **데이터 이동 검증:** 원본과 대상의 버전·행 수·검증 표식·애플리케이션 읽기/쓰기,
   실패 시 원본 유지와 접속 전환 복구를 실계정 드릴로 확인한다. 그 전에는
   자동 데이터 이전이나 무중단 이동을 약속하지 않는다.
5. **운영 경로 확장:** 대상별 비밀·네트워크·비용·헬스·롤백 정책과 CI/CD 연결을
   별도로 검증한다. 새 대상이나 온프레미스 실행기는 기능표와 위 검증을 통과한
   범위에서만 선택 가능하게 한다.

이 순서는 AWS 중심의 현재 구현을 버리지 않는다. 먼저 검증된 경로의 요구와
AWS 구현 사이 경계를 명확히 하고, 이후 같은 계약을 다른 실행 환경으로 확장한다.

현재 1단계의 일부로 정적 탐지 결과와 대상 어댑터 기능을 대조한
`infrastructure_plan.compatibility`를 작업에 기록한다. 이 표는 **OneDeploy가 지금
구현한 연결 기능**을 뜻하며, 클라우드 사업자의 전체 기능을 뜻하지 않는다.
AWS PostgreSQL은 명시적 DB 바인딩이 있을 때만 호환 판정한다. 모든 대상의 로컬
영속 파일·별도 워커는 아직 지원하지 않는다. 업로드가 거부되면 작업이 생성되지
않으므로 오류 응답에 근거를 제공하며, 무상태 여부는 정적 탐지만으로 확정하지
않는다. 업로드한 Dockerfile의 최종 `FROM --platform`이 리터럴 값으로 지정된
경우, AWS·Cloud Run의 `linux/amd64` 빌드와 충돌하면 업로드 및 AI 수정 뒤 재검사에서
배포를 거부한다. 빌드 단계만 다른 플랫폼이거나 `$TARGETPLATFORM` 같은 변수는
정적으로 충돌을 단정하지 않는다. 공개/비공개 네트워크·비밀 계약의 통합 검사와
실제 이미지 매니페스트의 아키텍처 검증은 이어질 작업이다.
