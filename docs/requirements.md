# 행사 원문과 OneDeploy 요구사항 대조

기준: 사용자가 제공한 `One Action, Infinite Clouds` 원문. 두 번째로 제공된 OneDeploy 제안서는
이전 설계 제안이며 행사 요구사항의 대체물이 아니다. `필수 방향`과 `예시`를 구분한다.

| 원문의 내용 | 해석 | 현재 구현 | 다음 검증 기준 |
| --- | --- | --- | --- |
| 로컬 웹 앱을 한 번의 동작으로 클라우드 또는 로컬에 배포 | 필수 방향 | 폴더/ZIP 업로드 → 배포 API → URL. Local Docker·AWS 실배포, Cloud Run 어댑터 | 실제 앱 업로드 한 번으로 외부 서비스 응답 확인 |
| AI를 활용해 코드를 자동 변경 | 필수 방향 | AI 함수 호출의 제한된 작업용 소스 패치, 실패 로그 기반 재시도 | 실제 모델 호출로 코드 변경·재배포 검증. 테스트 고정 응답과 구분 |
| 적절한 인프라 환경 구축 | 필수 방향 | 선택된 대상의 고정 기반 리소스 생성. PostgreSQL 앱은 탐지 근거와 기존 RDS·마이그레이션 연결을 계획에 기록한다. 검토한 신규 RDS 계획과 앱 ZIP을 한 작업으로 실행하는 경로는 실제 AWS에서 DB 생성·SQL 마이그레이션·ECS·HTTP 데이터 응답·정리까지 통과했다. 자동 대상 모드에서 명시적 DB 연결은 유일한 지원 대상인 AWS로 정책 선택하지만 앱별 적합성 판단은 여전히 제한적 | 고정 AI 응답을 실제 모델로 대체해 코드 변경 판단과 같은 데이터 경로를 검증 |
| 배포 위치·실행 방식, 로컬/클라우드 데이터·환경 차이, CI/CD·마이그레이션 고려 | 설계 문제 공간 | OCI 이미지·환경변수·어댑터로 실행 차이 일부 해소. AWS PostgreSQL 내부 경로와 서버 API 업로드의 마이그레이션·데이터 실계정 smoke 통과. CI/CD 연동은 없음 | 지원 범위와 미지원 시 차단 이유를 명확히 표시. UI 단일 흐름과 실패 복구는 별도 검증 |
| 여러 환경·프레임워크·앱 규모 | 확장 예시 | Local/AWS/Cloud Run, Node 또는 Dockerfile 앱. 동시 다중 대상 배포 아님 | 범위를 늘릴 때 동일 계획을 대상별로 검증하고 실패 독립성 확인 |
| SQLite→적절한 RDS, 모니터링 | 운영 품질 예시 | HTTP/소유 리소스 주기 검사와 DB 의존 탐지. PostgreSQL 신규 DB 경로는 부분 구현; SQLite 데이터 이전은 없음 | 영속 데이터 앱을 휘발성 경로에 무경고 배포하지 않음; 지원 시 생성·접속·마이그레이션·데이터 보존까지 검증 |
| 로그·롤백·Blue-Green/Canary | 안전성 예시 | 작업 로그, AWS 업데이트·릴리스 롤백, 자동 상태 확인 | 실제 실패·재배포 시 리소스 소유권과 활성 버전 검증 |
| 비용 효율·동시 팀 작업 | 운영 품질 예시 | 리소스 종료, 앱·대상 충돌 차단, 단일 서버 잠금 | 비용 가시화·동시 사용자 격리는 별도 확장. 완성으로 표시하지 않음 |
| 배포 시스템 자체의 품질 평가, 실제 배포 시연 | 명시적 평가 기준 | Docker/AWS 실배포 smoke. 실제 AI 판단은 아직 미검증 | 실제 AI + 실제 클라우드 조합의 1개 대표 경로를 끝까지 시연 |

## 설계 기준

1. 기존 어댑터는 실행기다. 앱에 맞는 인프라 판단은 별도 `요구 탐지 → 구조화된 계획 → 정책 검증` 단계가 맡는다.
2. 계획에는 근거 파일, 실행 대상, 공개 범위, 데이터 내구성, 필요한 리소스, 코드 변경, 비용·위험 근거를 기록한다.
3. AI가 임의 CLI나 인프라 코드를 실행하지 않는다. 서버가 지원 가능한 리소스·권한·비용 정책을 검증하고 소유권을 기록한다.
4. 모르는 의존성은 추측해 배포하지 않는다. 사용자에게 필요한 값을 요청하거나 명확한 차단 이유를 반환한다.
5. 성공은 모델 응답이 아니라 생성된 리소스와 실제 HTTP·데이터 경로 검사로 판정한다.

클라우드 사업자와 AI 도구는 자유롭게 선택할 수 있다. AWS·GCP·온프레미스를 모두 완성해야
한다는 조건은 없다. 한 번의 동작으로 실제 배포되는 지원 경로의 품질이 우선이다.

## 제출과 시연

행사 원문은 소스 코드 링크, 설계·논의 메모 전체 링크, 중간·최종 발표 자료 링크를 요구한다.
작업 중 설계 선택과 대안의 이유를 기록해야 한다. 최종 발표는 슬라이드 대신 설계 문서와
실제 배포 데모로 구성하며, 목업은 목업으로 표시해야 한다. 배포 대상 샘플 앱의 완성도보다
배포 시스템의 실제 동작을 보여주는 것이 중요하다. 현재 저장소의 설계·의사결정 기록과
smoke 테스트는 이 증빙의 출발점이다. 실제 모델 + AWS 전체 경로용 smoke 스크립트는 준비했지만,
API 키가 없는 개발 환경에서 아직 실행해 검증하지 못했다.

## 구현 순서

1. 앱 특성 탐지와 지원 범위 검증을 업로드 직후에 수행한다. SQLite·외부 데이터베이스·명시적 로컬 파일 저장·별도 워커 요구를 식별해 현재 단일 컨테이너 구성과 충돌하면 차단한다.
2. AI의 근거 있는 인프라 계획 도구를 추가한다. 사용자가 대상을 지정할 수도 있고, 자동 모드에서는 사용 가능한 대상 중 계획이 선택하도록 한다.
3. AWS의 영속 데이터용 리소스 경로를 하나 완성한다. 생성, 앱 접속 설정, 스키마 마이그레이션, 검증, 실패 복구, 비용·비밀 관리까지 같은 단위로 다룬다.
4. 실제 모델 + 실제 AWS의 무상태 경로와 데이터 경로를 검증하고, 발표에서는 검증한 범위만 시연한다.

현재 `3`의 DB 생성·검증·ECS 비밀 연결·SQL 마이그레이션은 각각 실계정에서
검증했다. 기존 RDS를 명시하는 서버 API·Chrome 데이터 경로도 통과했다. 신규
RDS 계획과 앱 업로드를 결합한 단일 작업은 실제 AWS에서 DB 생성 → 마이그레이션
→ HTTP 데이터 응답·자원 정리까지 통과했다. AI 도구 응답은 고정 테스트 값이었으므로
실제 모델의 코드 변경 판단은 여전히 검증해야 한다. 이 결과로 SQLite 등 기존 데이터 이전이나 전반적인 운영 품질을
주장하지 않는다.
AWS PostgreSQL 경로의 네트워크·비밀·데이터 보존 기준은 [AWS 영속 데이터 배포 경로 설계](aws-database-path.md)에 기록한다.
