2026-10-04까지 확인된 주요 흐름은 앱 업로드와 코드 준비, AWS ECS Express 배포,
기존·신규 PostgreSQL 연결, SQL 마이그레이션, HTTP 데이터 쓰기·읽기, RDS 스냅샷
복원·검사, 임시 DB의 최종 스냅샷 선행 폐기다. 각 흐름의 검증 범위와 남은 제한은
[현재 상태](status.md)에 구분해 적었다. 실제 AI 모델을 사용한 끝단 검증은
아직 남아 있으며, 브라우저의 유효 DB ID를 통한 폐기 실행은 통과했다. 실패 생성 정리 제품 경로는
로컬 모의 응답과 실제 Chrome에서 검증했으며 실계정 드릴은 아직 실행하지 않았다.
기존 RDS를 명시한 자동 대상 배포는 Chrome에서 VPC·서브넷 수동 입력 없이 ZIP을
업로드해 앱 소유 DB 바인딩과 AWS 정책 계획이 기록되는 것까지 확인했다. 이 로컬
드릴은 실제 에이전트 배포 실행을 막았으므로 공개 HTTP 성공 증거는 아니다.
보존된 AWS 자원의 Terraform 구성은 원격 상태를 새로 읽는 plan으로 다시 확인했다.
ECS Express provider의 제자리 갱신 1건이 남아 있어 apply하지 않았고, 이 변경과
예상 밖의 변경을 구분하되 어느 쪽도 자동 적용하지 않는 [plan 점검기](../terraform/aws-live/README.md)를 추가했다.
로컬에서만 실행하던 Python·Node 회귀 테스트는 GitHub Actions의 `main` 푸시와
PR에서도 실행하도록 연결했다. 이 자동 검증에는 AWS 자격 증명이나 실제 배포가 없다.
배포 시작 전 AI 준비 단계에는 취소 요청을 영속 기록하고 실제 배포 시도 직전 다시
검사하도록 했다. 첫 시도 이후에는 취소 요청을 거부하며 서버 재시작 때 미완료 취소
요청을 복원한다.
신규 RDS 생성과 앱 배포의 단계 사이에는 생성 작업 기록 상태를 검사하는 경계를
추가했다. AWS에서 DB가 조회돼도 생성 작업이 미확정이면 업로드를 중단하고,
완료 기록과 실제 DB 식별자가 일치할 때 배포 작업을 만든다.
검토한 신규 RDS 생성 계획을 앱 업로드에 결합하는 경로를 추가했다. ZIP을 먼저
검사하고 작업을 저장한 뒤 DB 생성을 시작하며, DB 성공 기록이 디스크에 저장되고
소유 DB 확인이 끝나면 같은 작업에서 앱 배포를 진행한다. UI에는 계획 확인 후
하나의 실행 버튼을 제공한다. 로컬 모의 AWS·재시작 테스트를 통과했고, 이후
2026-10-04 임시 앱의 실제 AWS 생성·배포·데이터 경로·정리도 통과했다.
생성 작업에는 고유 시도 ID를 저장하고 앱 배포 작업에도 같은 ID를 기록한다.
실패한 시도를 정리한 뒤 같은 앱 ID로 DB를 다시 만들더라도, 이전 배포 작업이
새 생성 결과를 자신의 결과로 받아들여 자동 배포하지 않도록 로컬 테스트로 확인했다.
실제 Chrome과 로컬 HTTP 서버에서 가격 계획 확인 → ZIP 업로드 → 생성 작업 원장 확정
→ 동일 작업의 배포 완료 표시도 검증했다. 이 로컬 드릴의 AWS 호출과 배포 실행은
모의 응답이다. 별도의 2026-10-04 실계정 드릴에서 같은 단일 작업을 검증했다.
단일 배포 작업이 끝나면 UI가 연결된 DB 생성 작업 상태를 다시 조회한다. 생성 실패
기록이 `needs_attention`이면 생성 영역을 열고 재확인·실패 스택 정리 버튼을 즉시
표시한다. 이 실패 화면도 실제 Chrome과 모의 AWS 응답으로 검증했다.
페이지를 새로고침한 뒤 이력의 해당 작업을 열면 앱·AWS 대상 입력을 맞추고 DB 생성
기록을 다시 조회한다. 같은 로컬 Chrome 드릴에서 복구 버튼이 다시 보이는지 확인했다.
실계정 브라우저 드릴에는 `--one-action-deploy` 모드를 준비했다. `--apply` 없이는
읽기 전용 네트워크 사전 점검 후 멈춘다. 사용자 승인 뒤 `--apply` 실계정 드릴을
실행했으며 중지된 기존 데모 자원은 유지했다.
모의 AWS를 사용하는 로컬 Chrome에서는 새 모드의 가격 계획→단일 업로드→
`PROBE_KEY` 입력 대기·재개를 실행했다. 실제 배포와 데이터 경로는 아래 실계정
드릴에서 별도로 검증했다.
서울 리전의 현재 AWS 계정에서 새 드릴의 `--apply` 없는 사전 점검을 통과했다.
리소스는 변경하지 않았다. 이후 로컬 Chrome에서 계획 가격이 제출 직전 달라지는
상황도 재현했다. 이 경우 생성 작업 원장이 없고 AWS 복구 버튼 없이 재계획 안내가
표시되며, 새로고침 후 이력에서 다시 열어도 같은 상태를 확인했다.
생성 완료 후 서버 중단으로 배포 연결이 끊긴 경우를 위한 명시적 재개 API·UI를
추가했다. 첫 배포 시도·AI 도구 실행·작업용 소스 변경이 없고 원래 생성 시도 ID,
DB 성공 기록, 실제 소유 DB가 일치하며 다른 활성 AWS 릴리스가 없을 때만 원래
작업의 앱 배포를 시작한다. RDS 생성은 반복하지 않는다. 재시작 복원 단위 테스트와
로컬 Chrome의 이력→수동 재개 흐름을 통과했으며 실계정 검증은 남아 있다.
수동 재개 전에 생성 작업의 원래 계정·리전·VPC·서브넷·서비스 보안 그룹과
업로드 당시 소스 체크섬을 다시 대조한다. 대기 중 소스나 DB 생성 요청 기록이
달라졌으면 기존 DB를 쓰는 새 배포로 시작하도록 거부한다.
한 버튼 작업의 DB 성공 뒤 실제 배포 에이전트 도구 호출까지 통합 테스트했다.
고정 제공자가 작업용 소스의 루프백 바인딩을 수정하고 실행 설정을 만든 뒤,
관리형 PostgreSQL 연결·SQL 마이그레이션과 수정된 소스를 AWS 어댑터 경계에
전달하는 것을 확인했다. 원본 소스는 보존하고 작업 이력에 변경 diff·시도 횟수·
완료 URL을 기록한다. 어댑터의 AWS 호출은 모의 응답이므로 실계정 배포 증거는 아니다.
실계정 한 버튼 드릴의 Chrome 연결 중단 복구를 보강했다. 이미 생성된 배포 작업
하나가 있으면 새 업로드·RDS 생성 요청 없이 이력에서 다시 열어 입력 대기 작업을
이어간다. 로컬 Chrome에서 연결을 나눠 검증했다. 2026-10-04 실계정 읽기 전용
사전 점검은 통과했지만 `--apply`는 AWS 일시 중지 해제 승인이 없다는 자동 검토에서
거부돼 AWS 자원은 변경하지 않았다.
이후 사용자 승인으로 같은 임시 앱 `dbdrill-1ddecda6`의 실계정 드릴을 실행했다.
Chrome에서 검토한 RDS 계획과 ZIP이 작업 `ed11706270f042b2` 하나로 접수됐고,
생성 시도 ID 일치·SQL 마이그레이션·ECS 배포·HTTPS 데이터 쓰기/읽기/삭제가
통과했다. RDS 대기 중 Chrome 연결이 끊겼지만 새 연결은 기존 작업을 열어
환경값을 입력했으며 생성 요청을 반복하지 않았다. 임시 ECS 종료 뒤 RDS·스택·
네트워크·이미지 태그를 정리했고 최종 AWS 조회에서 임시 자원 부재를 확인했다.
기존 `demo-app` RDS는 중지 상태로 유지했고, 실제 모델 판단은 시험하지 않았다.
실계정 드릴 정리 단계의 배포 상태 검사를 강화했다. 진행 중이거나 입력 대기 중인
작업, 실제 배포 시도 뒤 실패·중단된 작업, AWS 서비스 결과가 불확실한 작업이
있으면 DB·네트워크 자동 정리를 보류한다. 이 중단 조건은 로컬 단위 테스트로
검증했으며 새 단일 작업 모드의 실계정 실행도 2026-10-04 통과했다.
단일 작업의 계획 재검증이 RDS 생성 기록을 만들기 전에 실패하면 작업을 `failed`로
끝내고 가격 계획 재확인을 안내한다. 생성 기록이 남은 뒤의 시작 오류는 결과를
모르므로 `interrupted`로 남긴다. UI는 기록이 없는 실패에 AWS 복구 버튼을
표시하지 않는다. 두 분기는 로컬 서버·화면 테스트로 확인했다.

로컬 `.onedeploy/`에는 임시 작업의 원본 JSON·로그·ZIP과 식별자가 들어 있다.
이 폴더는 Git에서 제외하며 공유용 개발 기록으로 사용하지 않는다. 공유 가능한
결과와 판단 근거는 위 문서에 정리한다. 과거 변경 순서는 `git log --oneline`
으로 볼 수 있고, 코드 변경의 검증은 `python3 -m unittest discover -s tests`와
관련 UI 테스트에서 확인할 수 있다.

로컬 AI 스모크의 성공 판정을 강화했다. 실제 모델이 업로드 원본을 보존하고
`package.json` 시작 스크립트 및 `server.js`의 PORT·외부 바인딩을 작업용 복사본에
수정했는지 확인한다. 성공 뒤에는 배포 종료 API로 관리 Docker 컨테이너와 이미지
태그의 삭제도 검사한다. `--live --auto`는 예상치 못한 유료 클라우드 선택을 막기 위해
거부한다. Responses API의 stateless 추론 항목 재전달 형식은 공식 문서와 대조했으나,
당시 환경에 OpenAI 키·모델 설정이 없어 실제 모델 판단은 실행하지 못했다.
고정 응답의 로컬 Docker 스모크에서 두 번의 배포 시도, HTTP 응답, 종료 API의
컨테이너·이미지 삭제가 통과했고 Python 단위 테스트 353개가 통과했다.

인프라 요구 사전 검사의 조용한 절단을 수정했다. 기존에는 200개 또는 총 1 MiB를
읽으면 남은 파일을 검사하지 않았고, 개별 파일도 앞 20 KiB만 읽어 뒤쪽의 SQLite
의존성을 놓칠 수 있었다. 이제 최대 1000개·총 8 MiB·파일당 1 MiB 범위의 소스를
끝까지 읽고, 범위를 넘으면 배포 전에 명확히 중단한다. 25 KiB 뒤에 있는 SQLite
의존성 탐지와 파일 수·크기 초과 거부를 단위 테스트로 확인했다.

서버 재시작으로 `interrupted`가 된 로컬 Docker 에이전트 작업은 종전에는 성공한
배포만 허용하는 종료 API를 사용할 수 없어 수동 정리가 필요했다. 이제 기록된
1~3회 시도의 컨테이너·이미지 태그를 기존 소유권 검사로 정리하는 명시적 이력 버튼을
제공한다. 컨테이너 소유권이 달라지면 삭제를 거부하고 `delete_failed`로 남겨
재확인·재시도하게 했다. 재시작 복원, 시도 범위, 중복 요청 거부, 소유권 불일치와
화면 노출 조건을 로컬 테스트로 검증했다.
이어 실제 Docker에서 고정 AI 응답으로 두 번 시도해 HTTP 200을 얻은 뒤 결과를
기록하지 못한 서버 재시작 상황을 재현했다. 새 서버가 작업을 `interrupted`로
복원했고, `/api/jobs/{id}/retire` 호출 뒤 두 시도의 컨테이너·이미지 태그가 모두
없음을 Docker inspect로 확인했다. 명령은
`PYTHONPATH=. python3 tests/smoke_agent.py --interrupted-retire`다.

OpenAI API 키 없이도 제품의 Responses 연결 코드를 검증하도록 HTTP 전송 경계의
고정 응답 드릴을 추가했다. 실제 `OpenAIInfrastructurePlanner`와
`OpenAIDeployAgent`가 구조화된 자동 대상 계획, `store: false`의 추론 항목·함수
호출·도구 결과 재전달, 작업용 소스 수정, 로컬 Docker HTTP 성공과 종료 API를
통과했다. Docker 없는 동일 프로토콜 검사는 CI의 Python 테스트에 포함했다.
고정된 응답이므로 모델의 판단 품질이나 실제 API 접근 권한을 입증하지는 않는다.
신규 RDS와 앱 배포를 묶은 기존 통합 테스트도 고정 제공자 객체 대신 Responses
HTTP 전송 모의로 실행하도록 바꿨다. RDS 성공·소유권 확인 뒤 제품의
`OpenAIDeployAgent`가 추론 항목과 도구 결과를 이어 받아 원본은 유지하고 작업용
소스를 수정하며, 관리형 DB 요청과 SQL 마이그레이션을 모의 AWS 배포 어댑터에
전달하는 것을 확인했다. 이 검증은 실제 AWS 호출이나 모델 판단을 대체하지 않는다.

새 RDS의 기본 용량 견적에 선택적 서버 상한 `ONEDEPLOY_MAX_RDS_730H_USD`를
추가했다. 읽기 전용 생성 계획과 생성 요청 직전 재조회에서 730시간 인스턴스·
20 GiB gp3 견적을 검사한다. 견적이 없거나 상한을 넘으면 작업 기록과 AWS 생성
호출 이전에 거부한다. HTTP 계획 API에서도 설정값의 적용을 확인했다. 이 견적은
실제 청구액 전체를 포함하지 않으므로 총비용 통제로 설명하지 않는다.

OpenAI 모델 설정을 선택 사항으로 바꿨다. 공식 문서에서 Responses API·함수 호출·
구조화 출력 지원을 확인한 `gpt-5.4-mini`를 기본으로 사용하고, `ONEDEPLOY_AI_MODEL`을
설정하면 덮어쓴다. 이제 서버는 `OPENAI_API_KEY` 하나만 있어도 AI 계획·배포를
시작할 수 있다. 키 없이 실행하는 로컬 테스트에서는 실제 계정의 모델 접근이나
판단 품질을 검증하지 않았다.

AI가 작업용 소스를 고친 뒤 필수 환경값 입력을 기다리고, 서버 재시작 후 입력값을
받아 배포를 재개하는 경로를 검증했다. 원본 소스는 유지되고, 수정한 작업용 파일은
재사용되며, 입력값은 모델 이력과 작업 기록에 저장되지 않는다. 재개 시 작업 폴더가
사라졌다면 이전에는 원본을 조용히 다시 복사했지만, 이제 배포 전 실패로 기록한다.
이 검증은 고정 AI 응답과 모의 Docker 배포를 사용했다.

입력 대기 시 작업용 소스의 체크섬을 작업 기록에 저장하고, 환경값 재개 API에서
수정 여부를 확인한다. API 확인 뒤 워커가 시작되기 전에 파일이 바뀌는 경우에도
배포 도구 생성 시 같은 체크섬을 재검사한다. 변경되면 입력값을 작업 기록에
남기거나 배포 시도를 시작하지 않는다. 기존 체크섬이 없는 대기 작업은 작업 폴더
존재 검사만 적용한다.

AI의 `configure_deployment`가 만든 계획에는 당시 작업용 소스 체크섬이 있다.
`deploy_application`은 첫 시도 번호를 기록하기 전에 그 체크섬을 현재 소스와
비교한다. 계획 후 파일이 바뀌면 실행기를 호출하지 않고 다시 읽어 설정하도록
AI에 오류를 돌려준다. SQLite·지원하지 않는 DB 의존성이 새로 나타난 경우에는
기존 인프라 정책 검사의 구체적인 차단 이유를 먼저 반환한다. 정상 소스에서는
기존 이미지 빌더의 복사본 체크도 유지된다.

로컬 Docker 스모크에서 Responses HTTP 전송 고정 응답의 자동 대상 계획·코드 수정·
HTTP 성공·종료를 다시 확인했다. 별도 `--environment` 스모크는 환경값 입력 후
실패한 첫 Docker 시도를 수정해 두 번째 시도에서 HTTP 성공·종료를 확인했다.
`--environment --restart-before-resume` 드릴을 추가해 AI가 `package.json`과
서버 바인딩을 먼저 수정한 뒤 필수 환경값 대기로 멈추도록 했다. 서버 재시작 후
기록된 작업용 체크섬과 수정 파일을 확인하고, 환경값을 입력해 같은 소스로 Docker
HTTP 성공과 컨테이너·이미지 정리까지 통과했다. 모두 고정 AI 응답이며 OpenAI API나
AWS를 호출하지 않았다.

Responses API의 `incomplete_details.reason=max_output_tokens`를 구분해 표시한다.
[OpenAI 공식 문서](https://developers.openai.com/api/docs/guides/structured-outputs)는
이 상태에서 구조화 응답이 완성되지 않았을 수 있음을 명시한다. 계획기와 배포
에이전트는 부분 텍스트·함수 호출이 포함돼도 완료로 처리하지 않으며, 고정 응답
테스트로 실행기가 호출되지 않는 것을 확인했다. 실제 API 한도 도달은 재현하지 않았다.

AI 분석기와 인프라 계획기의 1 MiB 응답 상한 오류가 `AnalysisError`의
`ValueError` 상속 때문에 일반 연결 오류로 덮이는 문제를 수정했다. 두 호출 모두
상한 초과 시 원래 오류를 유지하며, 실제 네트워크 없이 경계 크기의 고정 응답으로
검증했다. 응답 본문을 오류 메시지에 포함하지 않는 기존 동작도 유지된다.

업로드 직후 AI 인프라 계획이 거부되면 작업 기록 전의 ZIP·추출 소스를 정리하는
기존 경로를 확인했다. 새 작업을 메모리에 등록한 직후 디스크 기록 저장이 실패한
경우에는 이전에 그 메모리 항목 때문에 업로드 디렉터리가 남았다. 이제 기록 파일이
없는 접수 실패 작업을 메모리에서 제거하고 디렉터리를 정리한다. 정리 자체가 실패하면
원래 오류를 유지하면서 서버 복구 경고에 작업 ID를 남긴다. 모의 계획 실패·저장
실패에서는 작업·디렉터리·워커가 남지 않는 것을 확인했다.

강제 종료로 예외 정리가 실행되지 않는 업로드에도 대비했다. 배포·분석 업로드
디렉터리를 만들자마자 `.uncommitted-upload` 표시를 쓰고, `job.json` 저장 후
표시를 지운다. 서버 재시작 시 표시가 있고 작업 기록이 없으며 업로드 중 생성될 수
있는 파일만 담긴 디렉터리는 정리한다. 알 수 없는 파일이나 작업 기록이 있으면
삭제하지 않고 복구 경고를 남긴다. 분석 API 실패 시에도 작업 기록이 없는 업로드를
즉시 정리한다. 로컬 재시작·실패 테스트를 통과했으며, 실제 프로세스 강제 종료는
주입하지 않았다.

ZIP 업로드의 전체 항목을 추출 전에 검사하도록 보강했다. 이전에는 같은 파일을
두 번 넣거나 파일을 상위 디렉터리로도 선언한 ZIP에서 앞 항목이 덮이거나 일부
파일만 먼저 풀릴 수 있었다. 이제 정규화한 경로의 중복과 파일·디렉터리 충돌을
거부한다. 폴더 업로드도 같은 ZIP 추출 경로를 거친다. 충돌 ZIP의 추출 대상에
파일이 생기지 않는 테스트와 기존 정상 업로드 테스트를 통과했다.

업로드 접수나 환경값 입력 후 작업 기록을 `running`으로 저장했지만 워커 스레드를
시작하지 못하는 경우를 복구했다. 이제 시작 실패를 `interrupted`와 이벤트로
디스크에 남기고 API에도 같은 상태를 반환한다. 입력된 환경값은 워커 시작 실패 시
메모리에서 지우며 작업 기록에 값 자체를 저장하지 않는다. 실제 워커 실행이나
클라우드 호출 없이 스레드 시작 실패를 주입해 확인했다.

배포 시도와 AI 도구 단계가 모두 0인 중단 작업은 이력에서 명시적으로 재개할 수
있다. 새 업로드는 원본 소스 체크섬을 기록하며, 재개 API는 원본·작업용 복사본이
접수 당시와 같은지 다시 검사한다. 이미 AI가 파일을 고쳤거나 배포 시도를 시작한
작업, 기존 릴리스를 갱신하던 AWS 작업, PostgreSQL 연결 작업은 이 경로에서
거부한다. 신규 DB 생성 후의 재개는 기존 별도 경로를 유지한다. 로컬 모의
워커 시작 실패→서버 재시작→명시적 재개와 소스 변경 거부를 검증했다. 실제
클라우드 재개 실행은 수행하지 않았다.

`smoke_agent.py --wire-fixture --resume-unstarted` 로컬 드릴을 추가했다. HTTP
업로드의 워커 시작 실패를 주입하고 서버를 새 인스턴스로 연 뒤, 인증 API로 같은
작업을 재개했다. Responses 전송은 고정 응답이지만 실제 에이전트 코드가 원본을
보존하며 소스를 수정하고 Docker HTTP 응답을 확인했다. 종료 API는 해당 컨테이너와
이미지 태그를 정리했다. AWS 및 실제 OpenAI 모델은 호출하지 않았다.

AI 배포 에이전트의 소스 읽기와 누적 요청 크기를 제한했다. `read_project_files`는
이제 파일 전체를 메모리에 읽기 전에 20,001자까지만 읽어 기존 20,000자 제한을
판정한다. Responses 요청 본문이 1 MiB를 넘으면 전송하지 않고 안전한 오류를
남긴다. 큰 파일·큰 작업 이력의 모의 테스트를 통과했다. 이는 실제 모델의 긴
작업 성공률을 개선했다는 뜻은 아니며, 요청 크기 초과를 명시적으로 차단한 것이다.

업로드 후 분석 경로도 큰 파일을 통째로 읽지 않도록 바꿨다. `package.json`은
인프라 사전 검사의 기존 파일당 1 MiB 상한과 맞추고, Dockerfile의 계획·AI
문맥 읽기는 각 40,000자·20,000자 경계에서 멈춘다. 원본 소스 SHA-256은
파일을 1 MiB 청크로 읽되 이전 체크섬 형식을 유지하고, 읽는 동안 크기가 바뀌면
중단한다. 큰 manifest·Dockerfile 거부와 큰 파일의 동일 체크섬을 테스트했다.

배포 에이전트의 OpenAI Responses 요청에서 일시적 서버 오류를 한 번만 재시도한다.
HTTP 500과 오류 코드가 일시적임을 나타내는 429·503에 한정하고, `Retry-After`가
있으면 이를 존중한다. 헤더가 없으면 짧은 지터 대기를 사용하며 8초를 넘는 대기나
두 번째 실패는 새 배포가 필요하다고 알린다. 사용 한도·잔액 오류, 연결 실패,
응답 수신 뒤의 처리 오류는 재전송하지 않는다. 재시도 위치는 배포 도구 실행 전의
AI 요청이므로 같은 요청에서 Docker/AWS 배포를 반복하지 않는다. [OpenAI 오류 코드
안내](https://developers.openai.com/api/docs/guides/error-codes)와 [속도 제한
안내](https://developers.openai.com/api/docs/guides/rate-limits)를 기준으로 했다.
고정 HTTP 오류 테스트로 분기를 검증했고 실제 OpenAI 계정의 제한 상황은 재현하지 않았다.

같은 Responses 전송 규칙을 업로드 분석기와 자동 인프라 계획기에도 적용했다.
세 단계가 공유하는 전송 함수는 공식 API 엔드포인트의 리디렉션을 따르지 않고,
응답을 최대 1 MiB까지만 읽는다. 서버가 HTTP 오류를 명시적으로 반환한 경우에만
일시성·대기 시간을 판단해 한 번 재시도한다. 연결 실패나 HTTP 성공 뒤의 잘못된
JSON은 재전송하지 않는다. 각 단계의 오류 메시지와 계획 결과 검증은 유지했다.
분석기의 503·지출 한도 429, 계획기의 500 회복을 고정 응답으로 검증했다.
실제 OpenAI 호출은 여전히 API 키 연결 후 확인해야 한다.

AI `apply_project_patch`의 파일 저장을 원자적 교체로 바꿨다. 패치 내용은 먼저
작업용 소스 바깥의 같은 작업 디렉터리에 임시 파일로 쓰고 동기화한 뒤 대상 파일과
교체한다. 교체 실패 시 원본 파일·기존 배포 계획·읽기 버전을 유지하고 임시 파일을
정리한다. 실행 권한이 있는 기존 파일은 해당 권한을 보존한다. 패치 직전 읽기도
40,000자에서 중단해 외부에서 갑자기 커진 파일을 통째로 읽지 않는다. 교체 실패,
실행 권한, 큰 파일 거부 테스트와 고정 AI 응답의 로컬 Docker 배포·종료를 통과했다.
프로세스 강제 종료 직후 디스크 내구성 전체를 보장한다는 뜻은 아니다.

AI 패치 도구의 응답에서 전체 diff를 제거했다. 변경 이력의 diff는 기존처럼 작업
기록에 보존해 로컬 UI에서 검토할 수 있고, 모델에는 변경 경로와 모델이 제출한
새 텍스트의 SHA-256만 반환한다. 반복 수정 시 같은 긴 diff를 다음 Responses
요청 이력에 다시 싣지 않아 1 MiB 요청 제한에 불필요하게 빨리 닿는 일을 줄인다.
전체 파일 체크섬은 비밀이 포함됐을 수도 있어 모델에 제공하지 않는다. 큰 패치의
도구 응답 크기와 작업 기록의 전체 diff 보존을 고정 응답으로 확인했다.

긴 AI 배포 작업에는 공식 [Responses 압축 안내](https://developers.openai.com/api/docs/guides/compaction)의
독립형 `/responses/compact`를 연결했다. `store: false`로 누적하던 요청이 768 KiB에
이르면 전체 현재 이력을 압축 엔드포인트로 보내고, 반환된 정식 출력 목록을 그대로
다음 Responses 입력으로 사용한다. 압축 결과가 원래 요청보다 작지 않거나 1 MiB를
넘으면 전송하지 않는다. 압축을 지원하지 않는 HTTP 400·404에서는 원래 요청이
1 MiB 이하일 때만 기존 방식으로 이어가며 같은 작업에서 압축을 반복하지 않는다.
압축 응답 형식이 잘못되면 기존 이력을 유지하고 중단한다. 고정 HTTP 응답으로
압축→후속 도구 호출·미지원 대체·형식 오류를 검증했다. 실제 모델의 압축 품질과
키 연결 후 동작은 아직 확인하지 않았다.

압축 경로를 배포 도구 순서까지 연결한 회귀 드릴을 추가했다. 고정 Responses 전송이
첫 파일 읽기 뒤 768 KiB를 넘는 암호화 추론 항목을 반환하면, 에이전트는 현재 이력을
`/responses/compact`로 보내고 반환된 압축 항목과 남은 도구 이력을 그대로 이어간다.
이후 원본을 보존하며 `package.json`·서버 바인딩을 수정하고 배포를 한 번만 실행한다.
CI의 모의 배포 테스트와 `smoke_agent.py --wire-fixture --compact-fixture`의 실제 로컬
Docker 빌드·HTTP 응답·종료 정리가 통과했다. 압축 결과 자체는 고정 응답이므로
실제 OpenAI 서비스의 판단 품질 검증으로 해석하지 않는다.

Dockerfile이 없는 실행형 Python 앱 경로를 추가했다. 루트의 `server.py` 또는
`app.py` 중 존재하는 파일 이름만 실행 항목으로 허용하고, `build_script`와 임의
명령은 거부한다. 기존 Dockerfile·Node `package.json` 경로를 우선한다. 생성
이미지는 Python 3.13, 선택적 `requirements.txt` 설치, 일반 사용자 실행,
설정된 `PORT`와 HTTP 확인을 사용한다. AI 안내도 Python 파일을 읽고 원본 대신
작업용 복사본의 바인딩·포트를 수정하도록 확장했다. 업로드 식별·계획 경계와
고정 Responses 전송의 로컬 Docker 배포·종료를 검증했다. 외부 의존성이 있는
다양한 Python 프레임워크와 실제 모델 판단은 아직 검증하지 않았다.

Dockerfile 없는 Python 배포에 루트 ASGI 진입점을 추가했다. `server.py`·`app.py`·
`main.py`의 `app` 객체를 선택하면 생성 이미지가 Uvicorn의 `module:app` 형식으로
실행한다. `requirements.txt`에 Uvicorn이 명시된 경우만 허용하고 실행 파일 이름과
이미지 명령 인자를 고정해 업로드에서 임의 실행 명령이 들어오지 않게 했다. FastAPI
예제를 ZIP으로 올린 고정 Responses 응답 드릴에서 계획·실제 Docker 빌드·HTTP
응답·종료 후 컨테이너와 이미지 태그 정리가 통과했다. CI용 모의 배포 테스트도
ASGI 도구 순서와 단일 배포 시도를 확인한다. 실제 모델 판단과 AWS ASGI 배포는
아직 검증하지 않았다.

Dockerfile 없는 Python 배포에 루트 WSGI 진입점을 추가했다. `server.py`·`app.py`·
`main.py`의 `app` 객체를 선택하면 생성 이미지가 Gunicorn의 `module:app` 형식으로
실행한다. `requirements.txt`에 Gunicorn이 명시된 경우만 허용하고 진입 파일과
명령 인자를 제한한다. Flask 예제의 고정 Responses 응답 드릴에서 실제 로컬
Docker 빌드·HTTP 응답·종료 후 컨테이너와 이미지 태그 정리를 확인했다.
CI용 모의 배포 테스트는 WSGI 도구 호출과 단일 배포 시도를 확인한다. 실제 모델
판단과 AWS WSGI 배포는 아직 검증하지 않았다.

Python 정적 분석의 진입 파일 선택을 보강했다. `server.py`가 있어도 그 파일을
무조건 먼저 실행하지 않고 루트의 `server.py`·`app.py`·`main.py`를 모두 살펴
하나로 특정되는 ASGI·WSGI `app` 객체를 선택한다. 객체 후보가 여러 개거나
Uvicorn·Gunicorn을 함께 설치해 서버 유형을 판별할 수 없으면 추측한 이미지
명령을 만들지 않고 오류를 반환한다. 여러 파일과 두 서버 의존성이 함께 있는
회귀 테스트를 추가했다. FastAPI에 Gunicorn만 있거나 Flask에 Uvicorn만 있는
경우도 필요한 서버를 명시하는 오류로 막는다. 기존 직접 실행형 Python 앱의 단일
파일 경로는 유지한다.

정적 Python 판별을 소스 실행 없는 구문 분석으로 바꿨다. 문자열 속의 `app = ...`나
함수 내부 변수를 서버 객체로 착각하지 않으며, 모듈 수준의 타입 주석이 붙은
`app` 할당은 인식한다. 루트 후보 파일은 개별 1 MiB 한도를 적용하고 구문 오류가
있으면 정적 실행 계획을 임의로 만들지 않는다.

생성 Python 이미지의 AWS PostgreSQL TLS 설정을 보강했다. 기존 RDS CA 번들을
이미지에 넣을 때 `PGSSLROOTCERT` 파일 경로를 함께 지정하고 ECS 환경은 Python에
`PGSSLMODE=verify-full`을 전달한다. Node의 기존 연결 프로필은 유지하며 기존
서비스 구성 재확인은 두 프로필을 구분해 검사한다. 앱 환경값으로 CA 경로를
덮어쓰는 요청은 DB 조회 전에 거부한다. 이미지·AWS 구성 단위 테스트를 통과했고
실제 Python 앱의 AWS DB 접속은 아직 검증하지 않았다.

Python DB 배포 완료 검사를 제출한 TLS 프로필에 맞췄다. 이전 리비전의 소유권을
읽기 전용으로 확인할 때는 기존 Node `require`와 새 Python `verify-full` 구성을
각각 허용하지만, 이번 리비전의 ECS 실행 구성은 요청한 런타임의 설정과 정확히
일치해야 성공 처리한다. 모의 ECS 응답에서 Python 설정을 Node 프로필로 낮추면
HTTP 확인 전에 배포 오류가 나고, 원래 설정이면 성공하는 회귀 테스트를 추가했다.

Python 관리형 PostgreSQL 경로를 로컬 TLS 데이터 드릴로 확장했다. Flask·Gunicorn·
Psycopg 예제는 기존 Node 프로브와 같은 SQL 마이그레이션, `PG*` 환경변수,
인증된 레코드 API를 제공한다. 임시 PostgreSQL의 서버 인증서를 테스트 CA로
서명해 Dockerfile 없는 Python 이미지를 빌드하고, `PGSSLMODE=verify-full`로
HTTP 쓰기·읽기·삭제를 통과했다. 동일 DB의 다른 네트워크 별칭과 다른 CA로
실행한 컨테이너는 각각 libpq의 호스트 이름 불일치·인증서 검증 오류를 확인했다.
임시 컨테이너·네트워크·이미지 태그는 정리했다. 실제 AWS RDS의 Python 접속은
아직 검증하지 않았다.

AWS PostgreSQL 데이터 경로 smoke에 `--probe-runtime python`을 추가했다. 첫
이미지 빌드가 생성 파일을 소스 복사본에 남기므로 v1·v2를 서로 다른 깨끗한
복사본에서 배포하도록 바꿨다. Python의 v2가 Dockerfile 앱으로 오인되어
`verify-full` TLS 프로필을 잃는 회귀를 막기 위한 변경이다. Node·Python
각각에서 마이그레이션 선행, 같은 서비스 업데이트, 기존 데이터 조회·삭제,
자원 정리 순서를 모의 어댑터로 확인했다. 실제 AWS `--apply`는 실행하지 않았다.

AWS PostgreSQL 스모크의 성공 판정을 임시 ECS 정리 이후로 옮겼다. 이전에는
서비스·이미지 정리에 실패해도 경고만 출력하고 프로세스가 성공 종료될 수 있었다.
이제 정리 실패는 예외로 전파하고, 이미 배포 오류가 발생한 경우에는 원래 오류에
정리 실패를 추가 기록한다. 두 상황을 회귀 테스트로 확인했다.

로컬 Python PostgreSQL TLS 드릴을 두 릴리스로 확장했다. v1·v2를 깨끗한
소스 사본에서 서로 다른 이미지로 빌드하고 같은 TLS DB에 v1이 쓴 행을 v2가
읽고 삭제했다. v2에서 다른 호스트 이름과 CA가 각각 거부되는 것도 실제 libpq
오류로 확인했다. 컨테이너·네트워크·이미지 정리가 끝난 뒤에만 PASS를 출력하도록
바꿨다. 실제 AWS 자원은 사용하지 않았다.

공통 이미지 빌더가 작업용 앱 폴더에 Dockerfile·CA·`.dockerignore`를 직접
기록하던 동작을 제거했다. 분석된 소스를 임시 빌드 폴더로 복사하고 복사 직후
체크섬을 재검사한 뒤 생성 파일을 그 폴더에만 넣는다. 빌드 성공·실패 모두 임시
폴더가 정리되고 원본의 체크섬과 Python 런타임 분석은 유지된다. 기존 Dockerfile과
CA 주입의 재빌드 단위 테스트, 실제 로컬 PostgreSQL TLS v1→v2 드릴, WSGI
서버 업로드→Docker HTTP·종료 드릴, 기존 Dockerfile HTTP 드릴을 통과했다.
