2026-10-03까지 확인된 주요 흐름은 앱 업로드와 코드 준비, AWS ECS Express 배포,
기존·신규 PostgreSQL 연결, SQL 마이그레이션, HTTP 데이터 쓰기·읽기, RDS 스냅샷
복원·검사, 임시 DB의 최종 스냅샷 선행 폐기다. 각 흐름의 검증 범위와 남은 제한은
[현재 상태](status.md)에 구분해 적었다. 실제 AI 모델을 사용한 끝단 검증은
아직 남아 있으며, 브라우저의 유효 DB ID를 통한 폐기 실행은 통과했다. 실패 생성 정리 제품 경로는
로컬 모의 응답과 실제 Chrome에서 검증했으며 실계정 드릴은 아직 실행하지 않았다.
기존 RDS를 명시한 자동 대상 배포는 Chrome에서 VPC·서브넷 수동 입력 없이 ZIP을
업로드해 앱 소유 DB 바인딩과 AWS 정책 계획이 기록되는 것까지 확인했다. 이 로컬
드릴은 실제 에이전트 배포 실행을 막았으므로 공개 HTTP 성공 증거는 아니다.
보존된 AWS 자원의 Terraform 구성은 원격 상태를 새로 읽는 plan으로 다시 확인했다.
ECS Express provider의 제자리 갱신 1건이 남아 있어 apply하지 않았고, 이 변경과
예상 밖의 변경을 구분하되 어느 쪽도 자동 적용하지 않는 [plan 점검기](../terraform/aws-live/README.md)를 추가했다.
로컬에서만 실행하던 Python·Node 회귀 테스트는 GitHub Actions의 `main` 푸시와
PR에서도 실행하도록 연결했다. 이 자동 검증에는 AWS 자격 증명이나 실제 배포가 없다.
배포 시작 전 AI 준비 단계에는 취소 요청을 영속 기록하고 실제 배포 시도 직전 다시
검사하도록 했다. 첫 시도 이후에는 취소 요청을 거부하며 서버 재시작 때 미완료 취소
요청을 복원한다.
신규 RDS 생성과 앱 배포의 단계 사이에는 생성 작업 기록 상태를 검사하는 경계를
추가했다. AWS에서 DB가 조회돼도 생성 작업이 미확정이면 업로드를 중단하고,
완료 기록과 실제 DB 식별자가 일치할 때 배포 작업을 만든다.
검토한 신규 RDS 생성 계획을 앱 업로드에 결합하는 경로를 추가했다. ZIP을 먼저
검사하고 작업을 저장한 뒤 DB 생성을 시작하며, DB 성공 기록이 디스크에 저장되고
소유 DB 확인이 끝나면 같은 작업에서 앱 배포를 진행한다. UI에는 계획 확인 후
하나의 실행 버튼을 제공한다. 로컬 모의 AWS·재시작 테스트를 통과했으며 실제 AWS
생성·배포 실행은 아직 하지 않았다.
생성 작업에는 고유 시도 ID를 저장하고 앱 배포 작업에도 같은 ID를 기록한다.
실패한 시도를 정리한 뒤 같은 앱 ID로 DB를 다시 만들더라도, 이전 배포 작업이
새 생성 결과를 자신의 결과로 받아들여 자동 배포하지 않도록 로컬 테스트로 확인했다.
실제 Chrome과 로컬 HTTP 서버에서 가격 계획 확인 → ZIP 업로드 → 생성 작업 원장 확정
→ 동일 작업의 배포 완료 표시도 검증했다. AWS 호출과 배포 실행은 모의 응답이며,
실계정 한 번 배포 성공의 증거로 사용하지 않는다.
단일 배포 작업이 끝나면 UI가 연결된 DB 생성 작업 상태를 다시 조회한다. 생성 실패
기록이 `needs_attention`이면 생성 영역을 열고 재확인·실패 스택 정리 버튼을 즉시
표시한다. 이 실패 화면도 실제 Chrome과 모의 AWS 응답으로 검증했다.
페이지를 새로고침한 뒤 이력의 해당 작업을 열면 앱·AWS 대상 입력을 맞추고 DB 생성
기록을 다시 조회한다. 같은 로컬 Chrome 드릴에서 복구 버튼이 다시 보이는지 확인했다.
실계정 브라우저 드릴에는 `--one-action-deploy` 모드를 준비했다. `--apply` 없이는
읽기 전용 네트워크 사전 점검 후 멈추며, 실제 임시 리소스 생성·단일 작업 검증은
AWS 중지 상태가 끝난 뒤 별도로 실행해야 한다.
모의 AWS를 사용하는 로컬 Chrome에서는 새 모드의 가격 계획→단일 업로드→
`PROBE_KEY` 입력 대기·재개를 실행했다. 실제 배포와 데이터 경로는 미검증이다.
서울 리전의 현재 AWS 계정에서 새 드릴의 `--apply` 없는 사전 점검을 통과했다.
리소스는 변경하지 않았다. 이후 로컬 Chrome에서 계획 가격이 제출 직전 달라지는
상황도 재현했다. 이 경우 생성 작업 원장이 없고 AWS 복구 버튼 없이 재계획 안내가
표시되며, 새로고침 후 이력에서 다시 열어도 같은 상태를 확인했다.
생성 완료 후 서버 중단으로 배포 연결이 끊긴 경우를 위한 명시적 재개 API·UI를
추가했다. 첫 배포 시도·AI 도구 실행·작업용 소스 변경이 없고 원래 생성 시도 ID,
DB 성공 기록, 실제 소유 DB가 일치하며 다른 활성 AWS 릴리스가 없을 때만 원래
작업의 앱 배포를 시작한다. RDS 생성은 반복하지 않는다. 재시작 복원 단위 테스트와
로컬 Chrome의 이력→수동 재개 흐름을 통과했으며 실계정 검증은 남아 있다.
수동 재개 전에 생성 작업의 원래 계정·리전·VPC·서브넷·서비스 보안 그룹과
업로드 당시 소스 체크섬을 다시 대조한다. 대기 중 소스나 DB 생성 요청 기록이
달라졌으면 기존 DB를 쓰는 새 배포로 시작하도록 거부한다.
한 버튼 작업의 DB 성공 뒤 실제 배포 에이전트 도구 호출까지 통합 테스트했다.
고정 제공자가 작업용 소스의 루프백 바인딩을 수정하고 실행 설정을 만든 뒤,
관리형 PostgreSQL 연결·SQL 마이그레이션과 수정된 소스를 AWS 어댑터 경계에
전달하는 것을 확인했다. 원본 소스는 보존하고 작업 이력에 변경 diff·시도 횟수·
완료 URL을 기록한다. 어댑터의 AWS 호출은 모의 응답이므로 실계정 배포 증거는 아니다.
실계정 드릴 정리 단계의 배포 상태 검사를 강화했다. 진행 중이거나 입력 대기 중인
작업, 실제 배포 시도 뒤 실패·중단된 작업, AWS 서비스 결과가 불확실한 작업이
있으면 DB·네트워크 자동 정리를 보류한다. 이 중단 조건은 로컬 단위 테스트로
검증했으며 새 단일 작업 모드의 실계정 실행은 여전히 남아 있다.
단일 작업의 계획 재검증이 RDS 생성 기록을 만들기 전에 실패하면 작업을 `failed`로
끝내고 가격 계획 재확인을 안내한다. 생성 기록이 남은 뒤의 시작 오류는 결과를
모르므로 `interrupted`로 남긴다. UI는 기록이 없는 실패에 AWS 복구 버튼을
표시하지 않는다. 두 분기는 로컬 서버·화면 테스트로 확인했다.

로컬 `.onedeploy/`에는 임시 작업의 원본 JSON·로그·ZIP과 식별자가 들어 있다.
이 폴더는 Git에서 제외하며 공유용 개발 기록으로 사용하지 않는다. 공유 가능한
결과와 판단 근거는 위 문서에 정리한다. 과거 변경 순서는 `git log --oneline`
으로 볼 수 있고, 코드 변경의 검증은 `python3 -m unittest discover -s tests`와
관련 UI 테스트에서 확인할 수 있다.
