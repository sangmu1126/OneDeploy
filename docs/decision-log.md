# 의사결정 기록

## 2026-10-01 — 앱별 서비스 보안 그룹을 서버 DB 경로에 연결

- 서버의 고정 서비스 보안 그룹 ID가 없으면 앱 ID와 VPC가 일치하는 네트워크 스택을 읽기 전용으로 검증한 뒤 기존 RDS 조회·신규 RDS 계획·DB 앱 업로드에 사용한다. 업로드 작업에는 선택한 그룹 ID를 AWS 설정과 DB 요청에 함께 기록해 재시작 후에도 일치시킨다.
- 기존 고정 그룹 설정은 유지한다. 새 앱별 자동 선택은 모의 AWS 테스트만 통과했으며, 실제 네트워크 스택 생성·DB 배포는 아직 실행하지 않았다.

## 2026-10-01 — 기존 RDS를 사용하는 서버 API 업로드 검증

- `tests/smoke_aws_postgres_api.py`에서 로컬 서버에 PostgreSQL 샘플 ZIP을
  업로드하고, `PROBE_KEY` 입력 대기 후 재개했다. 작업은 기존 `demo-app` RDS의
  소유권을 확인하고 SQL 마이그레이션과 ECS 서비스를 실행했다.
- 공개 HTTP에서 DB 행 쓰기·읽기·삭제와 상태 API를 확인했다. 종료 API는 임시
  ECS 서비스와 ECR 이미지를 정리했고 RDS·비밀은 보존했다.
- AI 도구 호출은 고정 테스트 응답이었다. UI의 DB 생성·선택 경로와 실제 모델
  판단, 실패 복구 및 DB 폐기는 이 결과만으로 검증됐다고 표시하지 않는다.

## 2026-10-01 — PostgreSQL 실계정 데이터 경로

- 다른 ECS 서비스에 연결된 보안 그룹을 DB 앱에 재사용하면 접근 범위가 넓어진다.
  서비스 그룹에 앱별 소유 태그를 요구하고 `demo-app` 전용 그룹을 별도로 생성했다.
- 서울 리전에서 비공개·암호화·삭제 보호된 PostgreSQL 18.3 RDS 스택을 만들었다.
  첫 SQL 마이그레이션은 Node의 RDS CA 신뢰 부족으로 실패했다. 서버 인증을
  끄지 않고 AWS 공식 글로벌 CA 번들을 체크섬으로 고정해 실행 이미지에 넣었다.
- 실제 AWS smoke에서 마이그레이션·DB 쓰기/읽기·같은 ECS 서비스의 v1→v2
  업데이트 후 데이터 보존과 임시 서비스·이미지 정리를 확인했다. 실패한 첫
  마이그레이션의 태스크 정의·이미지 태그도 소유권 확인 후 정리했다.
- RDS·관리형 비밀·전용 서비스 보안 그룹은 유지되고 비용이 계속 발생한다.
  서버 API 업로드와 UI의 단일 사용자 흐름은 아직 별도로 검증해야 한다.

## 2026-10-01 — 앱 전용 서비스 보안 그룹 생성기 분리

- 신규 DB의 앱별 네트워크를 위해 인바운드가 비어 있는 ECS 서비스 보안 그룹을 별도 CloudFormation 스택으로 생성·검증하는 CLI를 추가했다. DB와 그룹 모두 앱 소유 태그를 사용하고, 실제 ECS 배포가 추가할 수 있는 단일 제한 규칙만 검증 시 허용한다.
- 기본 사전 점검은 서울 리전 실계정에서 읽기 전용으로 통과했다. 실제 그룹 생성과 UI의 앱별 자동 선택은 아직 실행·구현하지 않았다.

## 2026-10-01 — 기존 스택의 중복 생성 계획 차단

- 신규 DB 계획을 내기 전에 CloudFormation 스택 목록을 완전히 읽고, 앱 ID에서 정해지는 스택 이름이 있으면 상태·소유 태그와 관계없이 생성 계획을 거부한다. 삭제 완료 기록도 보수적으로 차단한다. 생성 요청 직전 다시 검사하고, 실제 생성은 CloudFormation의 동일 스택 이름 제약도 적용받는다.
- 기존 `demo-app` RDS가 있는 서울 리전에서 계획 API가 오류를 반환하고 로컬 생성 작업 기록을 만들지 않는 것을 확인했다.

## 2026-10-01 — 신규 RDS 생성 요청을 먼저 기록

- UI에서 생성 계획의 계정·네트워크·기본 용량 가격을 확인한 뒤에만 별도 생성 버튼이 나타난다. 서버는 15분짜리 계획 ID를 발급하고 요청 시 사전 점검을 반복해 변경된 가격·네트워크에서 생성을 막는다. 작업 기록을 디스크에 먼저 저장한 후 비동기 CloudFormation 생성을 호출한다.
- 재시작으로 `running` 기록이 남으면 `needs_attention`으로 바꾸고 자동 재시도하지 않는다. 사용자가 결과 재확인을 누르면 지정 계정·앱 소유 태그·스택 ARN을 확인하고 생성 완료 시 기존의 전체 RDS 검증을 다시 수행한다.
- 실제 AWS에서는 읽기 전용 계획, 잘못된 계획 ID 차단, 합성 중단 기록의 소유 스택 재확인까지 통과했다. 신규 DB를 추가 생성하는 UI 버튼 자체는 아직 실계정에서 실행하지 않았다.

## 2026-10-01 — 새 RDS 생성 계획을 배포 전에 표시

- UI의 AWS 대상에서 새 DB 생성 계획을 별도로 조회한다. 서버는 기존 `preflight()`로 계정, 앱 전용 서비스 보안 그룹, VPC·가용 영역, 주문 가능한 RDS 구성과 용량 가격을 확인한다. 생성 요청은 보내지 않는다.
- 인증 HTTP 계획 API를 서울 리전 실계정에서 읽기 전용으로 확인했다. 생성 실행은 중복 요청·서버 재시작·비용 승인 결과를 기록하고 재확인하는 경로를 만든 뒤 연결한다.

## 2026-10-01 — 실제 Chrome의 기존 RDS 배포 경로

- `tests/smoke_aws_postgres_browser.py --apply`로 Chrome이 OneDeploy UI의 RDS 조회, ZIP 선택·업로드, `PROBE_KEY` 입력·재개를 직접 수행했다. 서울 리전 ECS 서비스와 기존 RDS에 배포한 뒤 공개 HTTP로 DB 행 쓰기·읽기·삭제를 확인했다. 임시 ECS 서비스와 이미지 정리도 확인했다.
- 실제 OpenAI 모델 대신 고정 도구 응답을 사용했다. 따라서 UI·서버·AWS 연결은 검증했지만 모델의 분석·코드 수정 품질은 검증하지 않았다. RDS·비밀·전용 보안 그룹은 보존돼 비용이 계속 발생한다.

## 2026-10-01 — 앱 ID의 기존 RDS 읽기 전용 조회

- DB ID가 앱 ID로 고정된 현재 설계에 맞춰, 전체 RDS 목록 대신 해당 앱 인스턴스 하나만 조회한다. RDS의 VPC·서브넷을 얻은 뒤 기존 스택·보안 그룹·비밀 역할 소유권 검사를 모두 통과해야 UI에 네트워크 값을 보여준다.
- 인증 HTTP 조회를 서울 리전의 기존 `demo-app` RDS에서 읽기 전용으로 통과했다. 업로드 시 다시 소유권을 검사해 조회와 배포 사이의 설정 변경도 차단한다.

## 2026-10-01 — 기존 RDS를 UI에서 명시

- AWS ECS Express를 선택한 경우에만 기존 OneDeploy PostgreSQL RDS 사용 옵션을 표시한다. VPC와 서브넷은 사용자에게 입력받고, 서버가 고정된 AWS 계정·앱 전용 보안 그룹과 DB 소유권을 배포 전 재검증한다.
- UI 입력 검증과 업로드 헤더 전송 테스트는 통과했다. 실제 AWS의 데이터 경로는 서버 API에서 검증했으며, 브라우저에서의 실제 AI·AWS 끝단 검증은 아직 남아 있다. 새 DB 생성과 목록 탐색은 이 선택에 포함하지 않는다.

## 2026-09-30 — PostgreSQL 리소스 생성 경로 분리

- 앱 배포에서 DB를 곧바로 허용하지 않고, 명시적 `--apply`가 필요한 독립 생성 경로를 먼저 둔다. 계정·VPC·보안 그룹·두 가용 영역과 인스턴스 클래스 가용성을 읽기 전용으로 확인한 뒤 새 CloudFormation 스택만 만든다.
- RDS는 비공개·암호화·관리형 암호·삭제 보호·`Retain` 정책을 사용한다. 실패한 앱 배포나 ECS 종료가 데이터 폐기로 이어지지 않게 DB 수명주기를 분리한다.
- 비밀 주입, 마이그레이션, 실제 데이터 경로 검증과 종료 정책이 완성되기 전에는 DB 앱 차단을 해제하지 않는다. 생성 경로의 AWS 실계정 검증도 아직 없다.

## 2026-09-30 — ECS Express 추가 서비스 보안 그룹

- 기본 공개 배포와 URL 검증은 유지하면서, 기본 VPC의 기존 보안 그룹 하나를 태스크에 추가할 수 있게 한다. 최초에는 인바운드 규칙이 없어야 하며, ECS Express 배포 후에는 같은 VPC·계정의 단일 보안 그룹에서 앱 포트로 들어오는 규칙 하나만 허용한다. CIDR 공개 규칙은 거부한다.
- ECS 생성 요청과 실제 활성 구성에서 그룹 ID를 확인하고, 동일 앱 업데이트가 기존 그룹을 조용히 바꾸지 못하도록 작업 결과에 기록한다.
- 이 연결은 RDS 지원의 네트워크 준비 단계다. DB 생성·접속 검증이 없으므로 DB 의존 앱 차단은 유지한다.

## 2026-09-30 — AWS 대상 계정 고정과 DB 경로 분리

- UI/서버에서 AWS 대상을 쓰려면 `ONEDEPLOY_AWS_ACCOUNT_ID`를 설정한다. STS 계정이 다르면 CloudFormation 적용 전에 중단한다. 테스트·직접 어댑터 호출은 별도 계정 검증을 수행할 수 있도록 기존 생성자를 유지한다.
- RDS 생성만으로 PostgreSQL 앱을 지원한다고 볼 수 없다. ECS 서비스와 DB의 VPC 연결, Secrets Manager 권한, 마이그레이션, 데이터 보존·삭제 동작까지 하나의 검증 경로가 필요하다.
- 이 경계와 완료 기준을 `docs/aws-database-path.md`에 기록하고, 실제 경로가 완성되기 전에는 DB 의존 앱 차단을 유지한다.

## 2026-09-30 — 상태 저장·별도 워커 요구 탐지 확대

- 현재 어댑터는 단일 HTTP 컨테이너와 휘발성 파일 시스템만 제공한다. SQLite 코드뿐 아니라 업로드된 DB 파일, 외부 데이터베이스 의존성, 명시적 로컬 파일 저장, 별도 워커 스크립트·의존성도 이 구조와 맞지 않는다.
- 업로드 직후와 AI 코드 수정 뒤 배포 직전에 이 패턴을 검사한다. 확인되면 리소스 생성 전에 이유를 표시하고 차단한다.
- 정적 탐지는 알려진 패턴에 한정된다. 경로를 변수로 조립하는 파일 쓰기나 외부 작업 의존까지 모두 판별한다고 주장하지 않는다.
- 별도 DB·스토리지·워커를 실제로 프로비저닝하는 지원 경로가 마련되면 해당 유형별 차단을 해제한다.

## 2026-09-30 — 원문 요구에 맞춘 인프라 계획 확장

- 원문은 AI가 코드를 자동 변경하면서 적절한 인프라 환경을 구축하는 시스템을 요구한다.
- 현재 코드는 작업용 소스 수정과 AWS 기반 리소스 생성·실배포까지 연결하지만, 사용자가 대상을 고르고 인프라 형태는 거의 고정된다.
- 결정: 기존 배포 엔진은 유지하고 앱 요구 탐지 → 구조화된 인프라 계획 → 정책 검증 → 코드·리소스 실행 단계를 추가한다. 전면 재작성은 하지 않는다.
- 우선순위: 자동 대상 추천과 근거 표시, 영속 데이터 의존 감지 및 부적절한 배포 차단, 지원하는 DB 경로의 실제 생성·연결·검증 순서로 확장한다.
- 한계: 인프라를 AI가 임의 명령으로 생성하도록 하지 않는다. 계획에서 허용된 리소스만 어댑터가 만들며, 지원하지 않는 요구는 명시적 차단으로 처리한다.
- 행사 원문과 현재 구현의 차이를 `docs/requirements.md`에 추적한다. 두 번째 붙여넣기 문서는 이전 제안이며 행사 원문과 동일한 요구사항이 아니다.
- 첫 구현: 업로드 직후 알려진 SQLite 의존을 검사하고, 현재 영속 저장소가 없는 모든 대상에서 리소스 생성 전에 거부한다. AI가 작업용 소스에 SQLite를 추가해도 배포 직전에 다시 검사한다.
- 자동 선택: AI가 실제 소스 인용·대상·작업 유형·이유를 구조화해 제안한다. 서버가 현재 설정된 대상과 공개 허용, 인용 일치, 무상태 HTTP 지원 범위를 검증하고 선택 결과·고정 리소스 목록을 작업에 기록한다.
- 검증: 단위 테스트에서 불가능한 대상·가짜 근거·영속 저장 요구·공개 허용 없는 AWS 선택을 거부했다. 고정 테스트 응답으로 자동 대상 선택 → 폴더 업로드 → 실제 Docker 수정·배포·HTTP 응답을 확인했다. 실제 AI 판단은 미검증이다.

## 2026-09-27 — 첫 구현 범위

- 후보: 실패 진단 중심 Deploy Doctor / 앱 입력부터 배포까지 OneDeploy.
- 선택: OneDeploy. 실제 배포 시스템이라는 행사 요구와 직접 연결된다.
- PipeLens 비교: CI 실패 진단 구조는 참고하되 배포 실행 엔진은 별도로 필요하다.
- 첫 목표: Node.js ZIP → 정적 분석 → Dockerfile → Local Docker → HTTP 응답.
- 이유: AI 판단과 배포 실행 문제를 구분할 수 있는 동작 경로를 먼저 확보한다.
- 기술 선택: Python 표준 라이브러리 API와 간단한 웹 UI. 초기 설치 의존성을 줄인다.
- 감수한 한계: GitHub URL, AI, Cloud Run, 롤백, 기존 Dockerfile과 secret 입력 미지원.
- 사용자는 대상 환경을 선택하는 흐름으로 확장한다. 두 환경 동시 배포는 필수가 아니다.
- 미결정: AI provider, 클라우드 계정·리전, 팀별 역할과 최종 지원 프레임워크.

## 2026-09-27 — 첫 실제 배포 검증

## 2026-09-28 — Cloud Run 배포 경로

- 동일한 AI 파일 수정·재시도 흐름에서 배포 대상만 Local Docker 또는 Cloud Run으로 선택한다.
- 공통 이미지 빌더를 분리했다. Cloud Run 이미지는 `linux/amd64`로 빌드한다.

- 공개 여부는 사용자 선택으로만 결정한다. 기본 비공개 서비스는 ID 토큰을 사용해 접속을 확인한다.
- 기존 서비스는 덮어쓰지 않는다. 실패 정리에서는 이번 시도의 관리 라벨과 ID가 맞는 서비스만 삭제한다.
- 현재 환경에 `gcloud`, 프로젝트 ID, 리전 설정이 없어 실제 Cloud Run 배포 검증은 수행하지 못했다.
- 클라우드 명령·이미지 인증·환경변수 전달·HTTP 검증·실패 정리는 모의 CLI 결과를 사용해 검사했다.
- Cloud Run 대상을 선택한 작업이 기존 AI 수정 흐름과 클라우드 어댑터로 이어지는 경계 테스트를 통과했다.
- 공통 이미지 빌더 변경 후 Local Docker의 실제 실패→수정→배포 성공 smoke도 다시 통과했다.
- Cloud Run 실배포와 실제 AI 판단은 각각 클라우드 계정 설정과 API 키 설정이 없어 검증하지 못했다.

- 성공한 AWS 작업 화면에 종료 버튼과 비동기 종료 API를 추가했다. 서비스 종료 중·종료됨·실패 상태를 작업 이력에 기록한다.

- 이전 통합 smoke에서 이미 종료된 서비스를 대상으로 실계정 재시도 경로를 검증했다. 정상 동작 중인 데모 서비스의 종료 버튼은 실행하지 않았다.
- 서비스 소유권이 다른 경우 삭제를 막고, 실패 상태에서는 재시도를 허용하는 테스트를 추가했다.

## 2026-09-28 — 같은 앱의 AWS 재배포와 URL 유지

- 동일 앱 ID의 이전 AWS 릴리스가 있으면 계정·리전·서비스 ARN·관리 태그·현재 이미지·직전 배포 성공 상태를 확인하고 기존 ECS Express 서비스를 업데이트한다.
- 새 배포가 `SUCCESSFUL`이고 새 이미지가 활성 구성이며 기존 HTTPS URL에서 HTTP 200이 확인된 뒤에만 새 릴리스를 성공으로 기록한다. 이전 작업은 `superseded`로 표시한다.
- 실제 서울 리전 계정에서 임시 앱 v1→v2를 배포해 URL 유지와 v2 JSON 응답을 확인했다. 임시 ECS 서비스가 `INACTIVE`가 된 뒤 두 ECR 이미지 태그를 삭제했다. 기존 데모 서비스와 공유 스택은 유지했다.
- 첫 smoke에서 완료된 ECS 서비스의 `currentDeployment`가 비어 있어 검사를 수정했다. 완료 이력은 `list-service-deployments`로 확인한다.
- 실패한 업데이트가 시작된 뒤에는 진단과 AWS 자체 롤백을 위해 새 이미지 태그를 자동 삭제하지 않는다. OneDeploy의 수동 롤백과 이 이미지의 자동 정리는 아직 미구현이다.

## 2026-09-28 — AWS 업데이트 실패 상태 재확인

- 기존 서비스 업데이트 명령 직전에 이전 배포 ARN과 새 이미지 정보를 저장한다. 명령 호출 뒤 결과를 확인하지 못하면 AI의 자동 재시도를 중단한다. 호출 시간 초과로 접수 여부가 불확실한 경우도 포함한다. 이전 릴리스를 `needs_attention`으로 표시하고 동일 앱의 새 배포와 종료를 막는다. 서버 재시작 후에도 중단된 작업의 재확인이 가능하다.
- 실패 작업의 재확인 API는 새 ECS 배포가 종료됐는지 읽기 전용으로 확인한다. 새 이미지와 HTTP 200이 확인되면 새 릴리스를 성공으로 복구하고, 이전 이미지와 HTTP 200이 확인되면 기존 릴리스를 다시 활성화한다. 둘 다 확인되지 않으면 차단을 유지한다.
- 이 경로는 모의 AWS 응답으로 단위 검증했다. 실제 실패·롤백 상황의 AWS 통합 검증과 수동 롤백은 남아 있다.

## 2026-09-28 — AWS 업데이트 미접수·외부 복구 판정

- 시간 초과 뒤 AWS에 새 배포 이력이 없는 경우 즉시 차단을 풀지 않는다. 실패 또는 서버 재시작 시점부터 10분 이상 지난 뒤, 기존 배포 이력만 존재하고 ECS에 진행 중인 배포가 없으며 기존 이미지가 유일한 활성 구성이고 HTTP 200일 때 이전 릴리스를 다시 활성화한다.
- 새 배포나 외부에서 수행한 재배포가 기록된 경우에는 완료 상태, 관리 태그, 유일한 활성 이미지, HTTP 응답을 함께 확인한다. 혼합 이미지나 진행 중인 배포는 계속 확인 대기 상태로 둔다.
- 이 판정은 단위 테스트로 검증했다. AWS API 반영 지연이 10분을 넘거나 외부 변경이 동시에 발생하는 운영 상황은 별도의 실제 검증이 필요하다.
- 기존 데모 서비스를 읽기 전용으로 조회해 완료된 서비스의 `currentDeployment=null`, 단일 활성 이미지, `SUCCESSFUL` 배포 이력과 OneDeploy 관리 태그의 실제 응답 형식을 확인했다. 실패 상황을 실계정에서 유발하지는 않았다.

## 2026-09-28 — 실패한 AWS 업데이트 이미지 정리

- 이전 릴리스로 복구된 실패 작업에서만 이미지 정리 API와 버튼을 제공한다. 자동 삭제는 하지 않는다.
- ECR 삭제 직전에 실제 AWS 계정, 서비스 ARN·관리 태그, 진행 중인 배포 없음, 기존 이미지 단독 실행, 이전 릴리스 HTTP 200을 확인한다. 실패한 시도의 태그 하나만 삭제하며 `ImageNotFound`는 이미 정리된 상태로 취급한다.
- 정리 작업 중 같은 앱의 새 배포와 서비스 종료를 차단한다. 중단·실패 시 재시도할 수 있다. 이 경로는 단위 테스트로 검증했으며 실제 실패 이미지를 실계정에서 만들거나 지우지 않았다.

## 2026-09-28 — 진행 중 AWS 업데이트 롤백 요청

- ECS의 `stop-service-deployment --stop-type ROLLBACK`을 실패·중단된 업데이트에만 노출한다. 완료된 릴리스를 과거 버전으로 되돌리는 기능은 아직 없다.
- 실제 계정·서비스 ARN·관리 태그·현재 배포 ARN을 확인한다. ECS 서비스 배포의 이전·대상 리비전을 조회하고 각 태스크 정의의 `Main` 컨테이너 이미지가 OneDeploy의 이전·실패 시도 이미지와 일치할 때만 롤백을 요청한다. 이미 AWS에서 롤백 중이면 다시 요청하지 않는다.
- 요청 뒤에는 즉시 성공 처리하지 않고 기존 결과 재확인으로 ECS의 `ROLLBACK_SUCCESSFUL`, 이전 이미지 단독 실행, HTTP 200을 확인한다. 단위 테스트를 통과했고, 기존 데모 서비스의 태스크 정의 형식은 읽기 전용으로 확인했다. 진행 중 배포를 실계정에서 중단하는 검증은 아직 하지 않았다.

## 2026-09-28 — 완료된 AWS 릴리스의 직전 버전 복구

- 성공한 Express 배포마다 활성 태스크 정의 ARN을 기록한다. 새 릴리스가 성공하면 이전 작업 기록에도 원래 태스크 정의 ARN을 보완한다.
- 현재 서비스의 AWS 계정·관리 태그·완료 상태·현재 이미지를 확인하고, 이전 태스크 정의의 `Main` 이미지가 직전 성공 릴리스 기록과 일치할 때만 그 태스크 정의로 같은 서비스를 업데이트한다.
- 새 배포가 `SUCCESSFUL`이고 이전 이미지·태스크 정의·기존 공개 URL·HTTP 200을 확인한 뒤 활성 이력을 이전 릴리스로 되돌린다. 두 릴리스의 ECR 태그는 서비스 종료 시 함께 정리한다.
- AWS 요청 직전 상태를 저장한다. 결과가 불확실하면 자동 재시도를 멈추고 읽기 전용 재확인으로 실제 활성 이미지를 판정한다. 직전 릴리스만 대상이며 임의의 과거 릴리스 선택은 아직 지원하지 않는다.
- 서울 리전 임시 서비스에서 v1→v2 응답을 확인한 뒤 이전 태스크 정의로 재배포해 같은 HTTPS URL의 v1 응답이 돌아오는 것을 확인했다.
- 임시 서비스를 `INACTIVE`로 종료하고 두 ECR 태그를 삭제했다. 기존 데모 서비스와 공유 스택은 유지했다.
- 직전 릴리스로 롤백한 뒤 같은 앱 ID로 다시 배포한 경우, 서버 재시작 시 오래된 롤백 기록이 새 릴리스를 덮어쓰지 않게 복원 조건을 제한했다. 업로드 API→재배포→재시작 흐름과 새 릴리스 종료 이력을 회귀 테스트로 검증했다.
- 불확실한 롤백의 재확인은 활성 이미지뿐 아니라 태스크 정의 ARN도 비교한다. 같은 이미지를 다른 설정으로 실행하거나 두 구성이 함께 활성인 경우 이력을 자동 확정하지 않는다. 일반 상태 검사도 진행 중 배포와 혼합 구성을 정상으로 표시하지 않는다.
- 상태 검사에서 저장된 AWS HTTPS 주소를 ECS 활성 구성의 단일 공개 엔드포인트와 대조한다. 다른 서비스의 URL이 우연히 HTTP 200을 반환해도 정상으로 판정하지 않는다. 유지 중인 서울 리전 데모 서비스를 읽기 전용으로 검사해 이 조건과 HTTP 200을 확인했다.

## 2026-09-29 — AWS 과거 릴리스 선택 복구

- 완료된 릴리스 롤백 대상을 직전 버전에서 같은 ECS 서비스의 성공 이력으로 확장했다. 대상 작업 ID를 API 본문으로 받고, 계정·리전·서비스 ARN·공개 URL·이미지 이력·저장된 태스크 정의를 검증한다.

- 수정 후 새 임시 서비스에서 v1→v2→v3의 동일 URL 응답과 v3→v1 복구 응답을 확인했다. ECS 서비스를 종료하고 테스트 ECR 이미지 태그 3개를 삭제했다.

## 2026-09-29 — AWS 최초 배포 완료 판정

## 2026-09-29 — Python 앱 AWS 실계정 배포

- `package.json` 없이 Dockerfile을 가진 Python 앱을 원클릭 업로드 API에 보내 테스트용 고정 AI 도구 호출로 바인딩을 수정하고 ECS Express에 배포했다.
- 공개 HTTPS 200과 상태 API의 활성 이미지 확인이 통과했다. 임시 ECS 서비스가 `INACTIVE`로 전환됐고 해당 ECR 태그가 `ImageNotFoundException`으로 확인돼 정리 완료를 재검증했다.
- 이 smoke는 실제 AWS 배포 엔진을 검증했지만, 실제 AI API의 파일 판단은 테스트용 고정 응답으로 대체했다. 기존 데모 서비스와 공유 스택은 유지했다.
