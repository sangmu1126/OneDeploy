# 실패한 PostgreSQL 생성 정리

생성 작업이 `needs_attention`으로 끝났다면 먼저 AWS 생성 결과를 재확인한다. 앱 소유 스택이 `CREATE_COMPLETE`이면 기존 DB를 연결한다. `ROLLBACK_COMPLETE`라면 **실패 스택 정리 계획 확인**을 누른다. 이 조회는 AWS 리소스를 변경하지 않는다.

계획은 현재 AWS 계정과 앱 소유 스택 ARN·태그·종료 상태를 확인한다. 스택 리소스가 모두 `CREATE_FAILED` 또는 `DELETE_COMPLETE`여야 하며, 앱 DB 인스턴스와 수동 스냅샷이 없음을 전체 목록으로 확인한다. 페이지가 남거나 상태를 확정할 수 없으면 정리를 거부한다. RDS 템플릿의 DB에는 `DeletionPolicy: Retain`이 있으므로 롤백 스택 상태만 보고 안전하다고 판단하면 안 된다.

계획에서 표시한 스택 ARN을 입력하고 정리를 시작하면 작업을 먼저 로컬 기록에 남긴다. 그다음 보호 해제와 실패 스택 삭제를 실행하고 `DELETE_COMPLETE`, DB·수동 스냅샷 부재를 다시 확인한다. 성공한 생성 시도 기록은 `database-operations/cleaned-attempts/`에 보존한다. 이후 같은 앱 ID로 새 생성 계획을 요청할 수 있다. 새 계획과 실제 생성 요청 직전에 DB·수동 스냅샷 부재를 다시 확인한다. 기존 `DELETE_COMPLETE` 이력만 허용하며, 다른 활성 스택이 있으면 거부한다.

프로세스가 중단되거나 AWS 결과가 불확실해지면 자동으로 삭제를 재시도하지 않는다. 생성 상태 확인 → 정리 계획 재조회 → ARN 재확인 순서로 진행한다. 스택이 이미 `DELETE_COMPLETE`이면 삭제 명령을 반복하지 않고 DB·수동 스냅샷 부재를 재확인해 로컬 기록만 마감한다. 보존된 DB 또는 수동 스냅샷이 있으면 자동 정리가 막힌다. 이 경우 운영자가 실제 리소스와 데이터를 조사해야 한다.

서버 시작 시 생성 또는 정리 기록 JSON을 읽지 못하면 그 앱 ID의 새 생성·정리 계획을 막는다. 파일명으로 앱을 식별할 수 없는 손상 기록은 모든 새 RDS 생성·정리 계획을 막는다. 상태 조회와 읽기 전용 재확인은 계속 가능하며, 원본 기록을 복구하고 서버를 재시작해야 차단이 풀린다. 경고만 표시한 채 새 AWS 작업을 접수하면 이전 작업과 충돌할 수 있기 때문이다.

2026-10-03 현재 이 제품 경로는 **로컬 모의 AWS 응답으로 검증**했다. Python 단위·서버 테스트와 실제 Chrome에서 로컬 HTTP 서버를 통한 생성 기록 조회 → 정리 계획 → 잘못된 ARN 거부 → 정확한 ARN 정리 → 같은 앱 ID 재계획 표시를 통과했다. 이 Chrome 드릴은 예상 밖의 AWS 명령을 거부하며 실제 계정에 연결하지 않는다. 이전 실계정 드릴은 실패 스택의 읽기 전용 재확인과 시험 리소스 수동 정리까지 수행했으며, 새 API/UI의 실계정 실행은 아직 하지 않았다. 중지된 데모 RDS와 ECS는 이 작업으로 변경하지 않았다.

로컬 브라우저 드릴 실행: `python3 -m tests.smoke_local_postgres_recovery_browser`. Chrome과 Node.js가 필요하며 임시 프로필은 실행 후 제거한다.
