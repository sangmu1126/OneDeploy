## 확인된 경로

- Local Docker와 AWS ECS Express의 무상태 HTTP 앱은 실제 빌드·배포·HTTP 응답을 확인했다.
  AWS에서는 같은 앱 ID의 업데이트와 URL 유지도 확인했다. 이 실계정 경로의 AI 판단은
  테스트용 고정 응답이었다.
- Dockerfile 없는 직접 실행형 Python `server.py`·`app.py`·`main.py`와 루트의
  `app` 객체를 Uvicorn·Gunicorn으로 실행하는 ASGI·WSGI 앱은 고정 생성 이미지
  경로를 지원한다. `server.py` 샘플의 자동 대상 선택·소스 수정과 FastAPI·Flask
  샘플의 서버 설정은 고정 AI 응답을 거쳐 실제 로컬 Docker HTTP 확인·종료까지
  통과했다. ASGI·WSGI 경로는 각각 `requirements.txt`에 Uvicorn·Gunicorn 명시가
  필요하다. 실제 OpenAI 모델과 AWS의 ASGI·직접 실행형 Python 경로는 아직
  검증하지 않았다. WSGI PostgreSQL 경로는 아래 실계정 검증을 통과했다.
  Python 생성 이미지의 AWS PostgreSQL 연결 계획에는 RDS CA 경로와
  `PGSSLMODE=verify-full`을 추가했다. 이 설정을 쓰는 Flask·Psycopg 앱의
  실계정 RDS 연결과 HTTPS 데이터 경로는 2026-10-04 통과했다.
  배포 완료 확인은 이번 런타임이 요청한 TLS 프로필과 ECS의 실제 설정을 대조하며,
  Python 요청이 기존 Node 프로필로 바뀐 경우 성공 처리하지 않는다.
  공통 이미지 빌더는 검증한 소스를 임시 빌드 폴더에 복사해 Dockerfile·CA·
  `.dockerignore`를 넣고, 원본 작업용 소스와 체크섬을 보존한다. 로컬 Docker의
  Python WSGI·기존 Dockerfile 앱 배포와 PostgreSQL v1→v2 데이터 드릴로 확인했다.
  Python PostgreSQL 예제는 임시 로컬 TLS DB에서 서로 다른 v1·v2 이미지를
  빌드해 `verify-full` 연결·v1 쓰기·v2 읽기/삭제를 통과했다. 잘못된 호스트 이름과
  CA는 v2에서 실제 libpq 오류로 거부됐고 시험 Docker 자원 정리도 확인했다.
  이 드릴은 AWS 네트워크·RDS·ECS 접속을 검증하지 않는다.
  실계정용 PostgreSQL 업데이트 smoke는 `--probe-runtime python` 선택과
  릴리스별 깨끗한 소스 사본을 지원한다. 두 런타임의 배포·마이그레이션·HTTP
  순서는 모의 어댑터로 검증했다. 2026-10-05 Python 실계정 v1→v2 드릴에서는
  서로 다른 코드의 HTTP 버전 응답과 동일 서비스·URL 유지, v1이 쓴 DB 행의
  v2 조회·삭제, SQL 마이그레이션 재실행을 통과했다. 임시 ECS 서비스와 두 이미지
  태그는 정리했다. 이 드릴은 내부 AWS 어댑터 경로다.
  서버 API와 Chrome 배포 드릴도 Python ZIP을 선택할 수 있다. Python ZIP의
  업로드·기존 RDS 바인딩과 고정 AI 도구 호출의 WSGI 설정·마이그레이션 전달은
  로컬 모의 AWS에서 통과했다. Python API 옵션은 2026-10-04 서울 리전에서
  ZIP 업로드·환경값 재개·SQL 마이그레이션·ECS·HTTPS 데이터 쓰기/읽기/삭제·
  임시 서비스/이미지 종료를 통과했다. 2026-10-05에는 같은 제품 API의 Python
  v1→v2 ZIP 업로드·환경값 재개·동일 서비스/URL 업데이트, 이전 릴리스의
  `superseded` 기록과 DB 행 보존·삭제도 실계정에서 통과했다. 고정 AI 도구
  응답을 사용했다. 같은 날 실제 Chrome에서도 v1·v2 Python ZIP 업로드와
  입력 재개, 이전 릴리스 표시, 동일 서비스·URL의 v2 응답 및 DB 행 보존·삭제를
  통과했다. 첫 브라우저 시도는 디버그 연결이 끊겼지만 제품의 AWS 업데이트
  재확인으로 완료된 v2를 복구하고 임시 서비스를 종료했다. 재실행은 전체 드릴과
  임시 서비스·이미지 정리를 통과했다. 첫 시도의 시험용 DB 행 ID는 CloudWatch
  접근 로그에서 복원했고, 지정된 행만 조회·삭제하는 후속 드릴도 통과했다.
  자세한 범위는 실계정 검증 기록에 남겼다.
  새 RDS 생성과 같은 작업에서 Python 소스의 잘못된 `localhost` DB 연결을
  고정 Responses 도구 호출로 수정하고 WSGI 계획·관리형 DB·SQL 마이그레이션을
  배포 어댑터까지 전달하는 흐름도 모의 AWS에서 통과했다. 실제 모델 판단이나
  이 수정본의 실계정 HTTP 응답은 검증하지 않았다.
  여러 루트 Python 파일이 있으면 정적 분석이 각 파일을 1 MiB 범위에서 구문
  분석해 서버 객체 후보를 모두 확인하고,
  둘 이상이거나 서버 유형이 모호하면 실행 파일을 추측하지 않고 거부한다.
- 앱 업로드, 작업용 소스 변경, 자동 대상 선택, 배포 실패 재시도, 상태 확인,
  AWS 릴리스 복구 및 리소스 종료 코드가 있다. 실제 OpenAI API를 사용하는 끝단 검증은
  현재 개발 환경에 키가 없어 수행하지 못했다.
- 인프라 요구 사전 검사는 소스 전체를 정해진 범위 안에서 읽고, 파일 수·용량 한도를
  넘으면 배포 전에 거부한다. 기존처럼 한도 이후의 파일을 조용히 건너뛰어 DB 의존성을
  놓치는 경로는 차단했다. 정적 탐지 자체가 모든 의존성을 증명하지는 못한다.
  `package.json` 분석도 같은 1 MiB 파일 한도를 적용하고, Dockerfile 읽기와
  소스 체크섬 계산은 제한 읽기·청크 방식으로 처리한다.
- 사용자가 AWS PostgreSQL 연결을 명시하면 인프라 계획에 검증된 기존 RDS 바인딩,
  탐지 근거 파일과 일회성 SQL 마이그레이션 작업을 기록한다. UI에는 새로 생성하는
  리소스와 재사용하는 리소스를 혼동하지 않도록 사용·준비 리소스로 표시한다.
  자동 대상 선택에서 기존 RDS를 명시하면 유일한 지원 데이터 경로인 AWS ECS Express를
  정책으로 선택한다. 이 분기는 AI 대상 판단이라고 표시하지 않는다. UI 배포 요청은
  VPC·서브넷 입력 없이 서버가 앱 소유 RDS에서 연결 네트워크를 다시 확인한다.
  이 간소화 경로는 로컬 모의 AWS 테스트와 실제 Chrome의 업로드→인프라 계획
  기록까지 통과했다. Chrome 드릴은 배포 실행을 대체하지 않았으며 실계정
  재검증은 남아 있다.
- PostgreSQL 경로에는 RDS 스택 템플릿·읽기 전용 사전 점검·가격 조회·기존 DB
  바인딩·비밀 주입·SQL 마이그레이션·데이터 읽기/쓰기 smoke가 구현돼 있다.
  2026-10-01 서울 리전에서 `demo-app` 전용 보안 그룹과 PostgreSQL 18.3의
  `db.t4g.micro`/암호화된 `gp3` 20 GiB RDS 스택을 생성했다. 생성 후
  소유권·비공개·삭제 보호를 확인했고, 실제 ECS 일회성 SQL 마이그레이션,
  DB 쓰기/읽기, 동일 서비스 v1→v2 업데이트 뒤 데이터 보존을 통과했다.
  검증 행과 임시 ECS 서비스·이미지는 정리했다. 처음 실패한 TLS 마이그레이션
  태스크의 정의·이미지 태그도 소유권을 확인하고 별도로 정리했다.
  RDS·관리형 비밀·앱 전용 서비스 보안 그룹은 **계속 남아 비용이 발생한다.**
  기본 용량의 730시간 기준 공개 가격 20.87 USD는 총 청구액이 아니다.
  DB 앱 이미지에 RDS CA를 자동 포함하는 최종 빌더 경로로도 같은 실계정
  v1→v2 smoke를 다시 실행해 통과했다.
  내부 AWS 어댑터 smoke에 이어 서버 API의 ZIP 업로드 → `PROBE_KEY` 입력 대기·재개
  → 기존 DB 바인딩·마이그레이션 → HTTP 데이터 쓰기/읽기 → 종료 API까지
  2026-10-01 실계정에서 통과했다. UI에 앱 ID 기반 기존 RDS 조회와 명시적 사용
  경로를 추가했다. 인증 HTTP 조회 API는 실계정에서 읽기 전용으로 통과했다.
  실제 Chrome에서 기존 RDS 조회 → ZIP 업로드 → `PROBE_KEY` 입력·재개 → ECS 배포
  → HTTP DB 데이터 쓰기·읽기·삭제 → 임시 ECS 종료까지 통과했다. AI 도구 호출은
  고정 테스트 응답이었다. AWS 대상 UI에는 새 DB의 계정·네트워크·용량 가격을
  읽기 전용으로 검증하는 생성 계획 미리보기도 있다. 인증 HTTP 계획 API는 실제
  서울 리전에서 통과했다. 계획 확인 후 별도 버튼으로 비동기 CloudFormation 생성
  요청을 기록하고, 재시작 시 자동 재시도를 막으며 소유 스택을 재확인하는 경로가
  구현돼 있다. 기존 `demo-app` 스택의 중복 생성 계획 차단은 실계정 읽기 전용
  검증을 통과했다. 2026-10-02 임시 `dbdrill-*` 앱에서 실제 Chrome의 앱 전용
  네트워크 생성, RDS 계획·생성 요청과 완료 상태, 기존 DB 연결값 자동 입력을
  실계정에서 확인했다. 같은 임시 앱의 ZIP 업로드·환경값 입력·SQL 마이그레이션·
  ECS 배포·HTTP 데이터 쓰기/읽기/삭제와 ECS·DB·네트워크 정리도 한 흐름에서
  통과했다. 2026-10-03에는 별도 임시 앱에서 실제 Chrome의 폐기 계획·DB ID 입력·
  실행·완료 표시와 최종 스냅샷 선행 DB 삭제를 확인했다. 여러 DB 선택은 아직 없다.
- 기존 RDS의 소유권을 검사한 뒤 자동 백업 보존 기간·최근 복원 가능 시점·삭제 보호·
  수동 스냅샷 목록을 확인하는 인증 API와 UI가 있다. `demo-app` 실계정에서 읽기 전용
  조회 결과는 보존 7일, 삭제 보호 켜짐이다. 생성 전 수동 스냅샷은 0개였고
  2026-10-02 생성·재조회 후에는 1개다. 이후 이 스냅샷의 복원 시험을 통과했다.
- 수동 스냅샷의 앱 소유 DB 검사·ID 중복 검사·명시적 `--apply` 생성·소유 태그 재확인
  CLI가 있다. CLI의 `demo-app` 읽기 전용 계획도 실계정에서 통과했다.
- UI에는 수동 스냅샷 계획·별도 생성 버튼·작업 기록·상태 재확인 경로가 있다.
  실제 Chrome에서 `onedeploy-demo-app-backup-20261002`의 계획 확인 → 생성 요청 →
  AWS `available` 재확인을 통과했다. 원본 RDS는 계속 `available`이고 스냅샷은
  암호화·소유 태그를 확인해 보존했다. 백업 저장 비용이 발생할 수 있다.
- 보존한 스냅샷의 복원 드릴용 읽기 전용 계획 CLI가 있다. 실계정에서 원본·스냅샷의
  구성 일치, 새 DB ID의 빈 상태, 730시간 기준 기본 용량 견적을 확인했다.
  복원 전용 보안 그룹의 생성·양방향 규칙 제거·소유권 검사·미사용 시 정리 CLI도 있으며
  서울 리전에서 임시 그룹 생성·정리까지 통과했다. 복원 DB의 생성·소유권 조회·명시적
  삭제 CLI도 구현했다. 복원 데이터 검사 작업용 보안 그룹과 DB 5432 임시 연결·해제는
  서울 리전 임시 그룹으로 통과했다.
  복원 시작 전에 대상별 로컬 기록을 남기고 그룹·DB 생성 응답이 불확실하면
  읽기 전용으로 소유 그룹·DB를 재확인하는 CLI가 단위 테스트를 통과했다.
  이 CLI의 기본 사전 계획과 실제 복원 생성·소유권 재확인은 서울 리전에서 통과했다.
  SQL 검사 전용 이미지 문맥과 읽기 전용 원장·선택적 데이터 표식 검증 코드가 있다.
  ECS 태스크의 읽기 전용 계획, 이미지 빌드·ECR digest 확인, 작업 등록·시작·종료,
  CloudWatch SQL 결과 확인과 성공 후 정의·이미지 태그 정리 코드가 있다. 실제 복원
  DB에서 기존 마이그레이션 원장 1건의 이름·SHA-256 비교, ECS 종료 코드·성공 로그,
  이미지·태스크 정의 정리 재확인을 통과했다. 대상별 로컬 작업 기록과 단계별 식별자
  저장, 중단 후 읽기 전용 재확인을 사용했다. 검사 연결을 닫고 임시 복원 DB·격리 그룹을
  삭제했으며 기록을 `cleaned`로 마감했다. 원본 RDS와 수동 스냅샷은 보존했다.
  첫 스냅샷에는 데이터 표식이 없었다. 두 번째 실계정 드릴에서는 원본 DB에
  고유 표식 행을 기록한 뒤 새 수동 스냅샷을 만들고, 복원 DB의 원장 1건과 표식 행을
  함께 검증했다. CloudWatch 로그는 `marker_checked: true`를 기록했다. 원본 표식,
  임시 앱·ECS 작업·복원 DB·보안 그룹·시험용 스냅샷을 정리했고 기존 보존 스냅샷
  하나와 원본 RDS만 남았다.
  원본 RDS 관리형 비밀의 현재 버전 생성 시각을 스냅샷 시각과 비교하는 읽기 전용
  자격 증명 계획 CLI는 서울 리전에서 통과했다. 비밀번호 값은 조회하지 않았다.
- 새 앱의 서비스 네트워크를 위한 앱 전용 보안 그룹 CloudFormation 템플릿과
  `onedeploy.aws_network` 생성·소유권 점검 CLI가 있다. 기본 모드는 계정·기본 VPC·
  동일 스택 중복을 읽기 전용으로 검사하며 서울 리전 실계정에서 통과했다. 임시
  `netprobe-*` 스택의 실제 생성·소유권 검증·앱별 그룹 선택·정리도 통과했다.
  서버는 고정 그룹 ID가 없으면 앱 ID·VPC의
  네트워크 스택을 읽기 전용으로 검증해 기존 DB 조회·신규 DB 계획·업로드에 사용할
  그룹을 선택한다. UI에는 네트워크 계획 미리보기와 별도 생성 버튼, 디스크 작업
  기록·스택 ARN·재시작 후 읽기 전용 재확인도 있다. 이 UI 생성 HTTP 경로는 실제
  Chrome에서 임시 스택 생성·작업 기록 검증·정리를 통과했다. 기본 VPC와 가용 영역별 기본 서브넷을 자동 입력하는 조회는 서울 리전
  실계정 및 실제 Chrome의 읽기 전용 UI에서 통과했다. Chrome은 기존 RDS 조회와
  자동 입력 VPC의 일치도 확인했고 배포 작업은 만들지 않았다.
- Cloud Run은 어댑터와 테스트가 있지만 실제 GCP 배포는 검증하지 않았다.
- GitHub Actions는 `main` 푸시와 PR마다 Python 3.11·3.14 단위 테스트 및 Node 22의
  UI·PostgreSQL JavaScript 테스트를 실행한다. 클라우드 자격 증명과 실제 배포는
  포함하지 않아 실계정 smoke의 대체 증거는 아니다.
- AI가 소스를 준비하는 실행 중 작업은 첫 배포 시도가 시작되기 전까지 취소를 요청할
  수 있다. 요청은 작업 기록에 남기고 AI 응답·도구 경계에서 중단한다. 시도 이후에는
  취소를 거부해 불확실한 클라우드 결과를 취소 완료로 표시하지 않는다.
- AI 작업이 필수 환경값을 기다리는 동안 서버가 재시작되어도 작업용 소스의 수정은
  유지된다. 재개 시 작업 폴더가 사라졌다면 원본을 조용히 복사하지 않고 작업을
  실패로 기록한다. 입력 대기 시 작업용 소스 체크섬을 기록해 재개 API와 배포
  워커에서 파일 변경을 다시 검사한다. 고정 AI 응답으로 소스 수정 → 환경값 대기
  → 서버 재시작 → 실제 Docker HTTP 성공 → 종료 API 자원 삭제까지 확인했다.
- AI가 배포 설정을 만든 뒤 작업용 소스가 바뀌면 첫 배포 시도를 기록하거나
  실행기를 호출하기 전에 변경을 거부하고 파일 재검토·재설정을 요구한다.
- 작업 접수 뒤 워커를 시작하지 못하면 `interrupted`를 디스크와 API에 기록한다.
  AI 단계와 배포 시도가 모두 시작되지 않은 중단 작업은 원본·작업용 소스 체크섬과
  다른 활성 AWS 릴리스 부재를 확인한 뒤 이력에서 명시적으로 재개할 수 있다.
  기존 PostgreSQL 연결 및 이미 시작된 AWS 업데이트는 이 재개 경로에서 제외한다.
  워커 실패·서버 재시작·같은 작업 재개·실제 Docker HTTP 응답과 정리는 고정
  Responses 전송 드릴에서 통과했다. 실제 모델 또는 AWS 재개 검증은 아직 없다.
- Responses API가 출력 토큰 한도로 `incomplete`를 반환하면 계획·배포를
  완료로 취급하지 않는다. 부분적인 도구 호출도 실행하지 않고 원인을 표시한다.
- 에이전트의 개별 파일 읽기는 20,000자, 누적 Responses 요청 본문은 1 MiB로
  제한한다. 요청이 한도를 넘으면 API를 호출하지 않고 실패 이유를 기록한다.
- 첫 로컬 Docker 배포 시도 후 작업이 실패·중단되면 이력에서 명시적으로 시도 자원을
  정리할 수 있다. 서버는 기록된 시도 번호의 컨테이너·이미지 태그만 소유권을 검사해
  삭제하며, 소유권 불일치나 Docker 오류는 재시도 가능한 실패로 남긴다. 클라우드의
  불확실한 배포 결과에는 이 경로를 적용하지 않는다. 실제 Docker 스모크에서는
  HTTP 성공 후 결과 미기록 상황을 재현해 서버 재시작·`interrupted` 복원·종료 API의
  두 시도 자원 삭제까지 확인했다. AI 판단은 고정 테스트 응답이었다.

## 우선순위별 남은 작업

1. **AWS 생성 실패·롤백과 사용자 DB 폐기 절차.** 앱 전용 네트워크·새 DB 생성부터
   브라우저 ZIP 업로드·필수 값 입력·SQL 마이그레이션·ECS 배포·HTTP 데이터
   쓰기/읽기/삭제, ECS·DB·네트워크 정리까지 서울 리전 임시 앱에서 통과했다.
  생성 요청이 AWS에 접수된 직후 작업 프로세스를 종료하고 새 프로세스가
  `needs_attention` 기록을 읽어 실제 완료 스택을 재확인하는 경로도 통과했다.
   신규 DB 생성 기록이 `running`·`needs_attention`이면 같은 앱의 ZIP 배포를
   차단하고, `succeeded` 기록의 DB ID가 실제 소유 DB와 같을 때만 연결한다.
   기존 DB처럼 생성 기록이 없는 경우에도 AWS 소유권 검증은 계속 요구한다.
   검토한 RDS 생성 계획과 앱 ZIP을 함께 제출하는 경로를 추가했다. 소스·SQL·대상
   정책을 먼저 검사해 작업을 기록하고, RDS 생성이 디스크에 성공으로 확정된 뒤
   같은 작업에서 ECS 배포를 시작한다. 서버 재시작이나 생성 결과 불확실 시
   자동으로 다시 생성·배포하지 않는다. 이 연결 흐름은 로컬 모의 AWS 테스트와
   임시 앱의 실계정 한 번 배포 검증을 통과했다. 생성 시도 ID를 배포 작업에
   기록해 실패 정리 후 동일 앱 ID의 새 생성 시도로 오래된 배포 작업이 이어지지
   않도록 막는다. 실제 Chrome의 한 버튼 흐름은 2026-10-04 임시 앱
   `dbdrill-1ddecda6`에서 RDS 생성·SQL 마이그레이션·ECS 배포·HTTPS 데이터
   쓰기/읽기/삭제와 ECS·DB·네트워크 정리까지 통과했다.
   단일 작업의 생성 실패 후 `needs_attention` 기록과 재확인·정리 버튼이 화면에
   자동 표시되는 것도 로컬 Chrome에서 확인했다. 페이지 새로고침 후 이력에서
   중단된 작업을 다시 열어도 같은 복구 상태가 표시된다.
   이 경로의 실계정 Chrome 드릴은 [실계정 검증 기록](aws-postgres-live-runbook.md)에
   `--one-action-deploy` 모드로 기록했다.
   같은 모드의 서울 리전 읽기 전용 사전 점검은 2026-10-03 통과했다. 생성 계획
   변경 시 재계획 안내가 이력 재진입 후에도 유지되는 것은 로컬 Chrome에서 확인했다.
   2026-10-04 읽기 전용 사전 점검도 통과했다. 최초 `--apply` 시도는 AWS 일시 중지
   해제 승인 부재로 자동 검토에서 거부됐고, 이후 사용자 승인으로 실계정 실행을
   완료했다. Chrome 디버그 연결이 실제 RDS 생성 대기 중 끊겼지만 기존 단일 작업에
   재접속해 필수 값을 입력했다. DB 생성 요청은 반복하지 않았다. 임시 ECS는
   `INACTIVE`, 임시 RDS·활성 DB/네트워크 스택·스냅샷·이미지 태그·실행 태스크는
   최종 조회에서 없었다. 기존 `demo-app` RDS는 `stopped`로 유지됐다.
   고정 AI 도구 응답의 통합 테스트에서는 같은 작업에서 소스 수정·실행 설정·
   관리형 DB/SQL 마이그레이션을 AWS 어댑터 경계까지 전달하고 원본 보존을 확인했다.
   어댑터 AWS 호출은 모의 응답이며 실제 모델 호출이나 빌드를 대체하지 않는다.
   생성 완료 후 서버 중단으로 끊긴 작업은 첫 배포 시도·AI 단계·작업용 소스 수정이
   시작되지 않은 경우에만 사용자가 명시적으로 앱 배포를 재개할 수 있다. 원래 생성
   시도·원래 생성 요청 설정·소스 체크섬·실제 DB 소유권·다른 활성 릴리스 부재를
   재검사하며 RDS 생성은 반복하지
   않는다. 로컬 재시작·Chrome 드릴은 통과했고 실계정 재개 검증은 남아 있다.
   가격 계획 재검증이 생성 요청 기록 전에 실패하면 재계획 가능한 `failed`로,
   생성 기록이 남은 뒤의 시작 오류는 결과 확인이 필요한 `interrupted`로 구분한다.
   일반 사용자의 명시적 DB 폐기 CLI·인증 API·UI를 추가했다. 최종 암호화 수동
   스냅샷의 `available` 확인을 DB 삭제의 선행 조건으로 두고, 소유권·ECS 비밀 사용·
   삭제 보호·스택 상태를 검사하며, 접수 작업은 로컬에 먼저 기록하고 재시작 때
   자동 재시도하지 않는다. `demo-app`의 읽기 전용 폐기 계획은 실계정에서 통과했다.
   임시 `retire-*` 앱에서 공통 폐기 실행기의 최종 스냅샷 `available` 확인 → DB
   삭제 → RDS 스택 삭제를 실계정 검증했다. 시험용 스냅샷·네트워크도 정리했으며
   기존 `demo-app` DB와 보존 스냅샷은 정상 상태다. 실제 Chrome에서 폐기 계획
   표시·잘못된 DB ID 거부·작업 기록 부재도 확인했다. 별도 임시 `dbdrill-*` 앱에서
   실제 Chrome의 유효 DB ID 폐기 실행·완료 표시와 시험용 스냅샷·네트워크 정리도
   통과했다. 2026-10-03 실제 AWS의 실패 전용 CloudFormation 스택을 이용한
   롤백 드릴에서 생성 작업의 `needs_attention` 전환, 앱 소유 `ROLLBACK_COMPLETE`
   읽기 전용 재확인, 시험 스택·네트워크 정리도 통과했다. 일반 UI에
   [실패 생성 정리 경로](aws-postgres-failed-create-recovery.md)를 추가했다.
   로컬 모의 AWS 응답과 실제 Chrome의 HTTP/UI 흐름까지 통과했다. 이 경로의
   실계정 실행 검증은 아직 남아 있으며, 중지된 데모 자원은 변경하지 않았다.
2. **데이터 수명주기와 복구 검증.** 앱 배포 실패·업데이트·서비스 종료가 DB를
   삭제하지 않는지 실계정에서 확인한다. 백업 설정 조회와 명시적 수동 스냅샷
   CLI·UI 생성과 스냅샷 `available` 실계정 확인, 복원 인스턴스 생성·SQL 원장 검증·
   임시 리소스 정리까지 통과했다. 두 번째 드릴에서는 스냅샷 이전에 기록한
   애플리케이션 데이터 표식의 실제 복원 비교도 통과했다. 실패 복구 실계정 훈련과
   제품 폐기 UI의 실제 임시 DB 클릭 검증도 통과했다.
   SQLite의 기존 데이터 이전도 지원하지 않는다.
3. **실제 AI 끝단 검증.** 사용 가능한 API 키로 코드 변경 판단과 자동 대상 선택을
   실제 호출하고, 업로드부터 AWS HTTP 응답까지 실행한다. 고정 응답 smoke의 결과를
   실제 모델 정확도 증거로 사용하지 않는다. 로컬 Docker의 `smoke_agent.py --live`는
   원본 보존, 작업용 소스 수정, HTTP 성공, 배포 종료 API의 자원 삭제까지 검사하도록
   준비했다. Responses HTTP 전송만 고정한 `--wire-fixture` 드릴은 실제 AI 계획기와
   에이전트 코드의 요청 형식·추론 항목·도구 결과 재전달부터 Docker 배포·정리까지
   통과했다. 같은 경로의 Docker 없는 검증과 신규 RDS 생성 성공 뒤 실제
   `OpenAIDeployAgent`가 소스 수정·관리형 DB·SQL 마이그레이션을 모의 AWS 어댑터에
   전달하는 검증은 CI에 포함했다. 모델 기본값은 `gpt-5.4-mini`이고 현재 환경에는 API 키가 없어 실제 모델 실행
   결과는 아직 없다.
4. **운영 범위 확장.** Cloud Run 실계정 검증, 다중 사용자 격리, 첫 배포 시도 이후 실행 중 취소,
   실제 청구액 예산 통제, CI에서 실제 배포까지의 연동, 비 AWS 대상의 URL 고정·릴리스 복구는 남아 있다.
   새 RDS에는 선택적 `ONEDEPLOY_MAX_RDS_730H_USD` 상한을 두어 계획과 생성 직전의
   인스턴스 730시간·기본 gp3 20 GiB 견적을 검사한다. 다른 AWS 비용은 포함하지 않는다.
   이들은 AWS PostgreSQL 단일 경로를 완성하는 작업보다 후순위다.

실계정 생성·검증 절차와 보존된 리소스는 [실계정 검증 기록](aws-postgres-live-runbook.md)에 남겼다.

현재 일반 UI에서는 영속 DB·파일 저장·별도 워커가 필요한 앱을 차단한다.
단, AWS ECS Express 대상으로 기존 OneDeploy PostgreSQL을 명시하고 서버 사전 검증을 통과하면 DB 앱을 배포할 수 있다. UI의 이 경로는 고정 AI 도구 응답으로 실계정에서 검증했다. 실제 모델 판단은 별도로 남아 있다.
